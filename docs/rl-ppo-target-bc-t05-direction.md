# PPO от target BC при T=0,5

> Исторический протокол / исходная спецификация. Путь сохранён: документ используется конфигурацией или кодом.
> Это условия отдельного этапа, а не актуальный общий справочник; наличие плана не доказывает запуск.
> Проверенные статусы и ограничения: [журнал](experiment-ledger.md); текущее устройство: [справочник](rl-architecture.md).

2026-11-07. Направление одного следующего опыта. Этот документ не запускает
обучение и не арендует машину.

## Цель и основание

Исходный BC epoch 10 на одинаковых 128 development случаях дал 27 побед
в argmax, одну при sampling T=1 и 13 при T=0,5. Разность T=0,5−T=1:
+9,375 п.п., paired world CI [6,25; 12,50]. Предусмотренное основание для
нового PPO получено. Дополнительный перебор температур не нужен.

Задача запуска — получить прирост argmax-побед над BC на целевой смеси:
карты 10/12/16, армии 5–13 всех пяти типов. Более частые sampling-победы
нужны как обучающий сигнал; сами по себе они не являются результатом PPO.
Практический ориентир — 25–30% побед на additional; цель 75% остаётся
дальней и не обещается этим запуском.

## Основные параметры

Переиспользовать runner PPO после target BC. Основное изменение — одна
постоянная температура 0,5 во всём распределении действий. Сохранить
остальные условия предыдущего ограниченного PPO.

| Параметр | Значение |
|---|---|
| Родитель | `artifacts/rl/cp-imitation-target-scale/checkpoints/epoch-10.pt` |
| Инициализация | Все веса BC; новый PPO Adam, без optimizer BC/неудачного PPO |
| Модель и точность | C/GRU; BF16 spatial, остальное FP32; block 32, padding 256 |
| Температура | T=0,5 постоянно, без schedule |
| PPO Adam | LR 1e−5; betas 0,9/0,999; eps 1e−5; weight decay 0 |
| Rollout / Adam batch | ≥8192 реальных позиций / 1024, включая forced для value |
| GRU / microbatch | Фрагмент 128 / 8; прежняя фактическая история и prefix replay |
| PPO | До 4 эпох; clip 0,2; value coefficient 0,5; entropy coefficient 0 |
| Gradient clipping | 0,5 |
| KL | Полный old || current по свободным ≤0,015; прежний rollback |
| Награда | Win/draw/loss = 1/0/0; gamma=lambda=1; полные эпизоды |
| Бюджет | 2 097 152 новых решения или 7200 активных секунд |

Обычный CP, исправленный TargetFactory, 57 training-worlds, все прежние
категории армий, стороны и оба типа старта, 30 раундов. Не исключать 16×16
из-за слабого текущего результата. Параллелизм взять из уже измеренного
режима конкретной машины; новая кампания оптимизации не входит в опыт.

Seed 17, новые namespaces `ppo_target_bc_t05_train_v1`,
`ppo_target_bc_t05_shuffle_v1`, `ppo_target_bc_t05_critic_v1`;
episode ID и бюджет с нуля. Это новый опыт, а не resume T=1.

## Температура должна описывать одну обучаемую политику

Использовать `log_softmax(logits / 0.5)` по легальным действиям в collector,
сохранённых old_logp и полных behavior distributions, текущих PPO logp/ratio,
entropy, полном KL и behavior replay. Обновить также фактически используемый
ускоренный путь PPO. Делить logits один раз; logits самой сети и value
не масштабировать. Для argmax оставить прежний выбор максимума.

Конфигурация и checkpoint сохраняют T; resume не меняет её. Режим/T входят
в ключ оценочного кеша. Нельзя смешивать старые rollout T=1 с новым опытом.
Текущее расширение RLAgent из sampling-оценки само по себе не меняет PPO
collector: эту связь нужно реализовать явно.

Достаточна узкая проверка математической согласованности: до изменения
весов replay первого штатного rollout даёт прежнюю численную точность
совпадения behavior/current, ratio около 1 и KL около 0 при T=0,5;
forced не дают actor-gradient. Отдельный небольшой пример с ненулевыми
различиями logits должен сравнить реализованный PPO loss/gradient с явным
`log_softmax(logits / T)`: нулевой KL один не доказывает правильность loss.
Не повторять полный suite и неизменённые CP/rollback-проверки.

## Critic и границы

Сохранить существующую подготовку всей value head на первом штатном rollout
при замороженных encoder/GRU/policy: отдельный Adam LR 1e−4, batch 1024,
MSE, clipping 0,5; максимум два прохода или 120 секунд с конца collection,
включая извлечение признаков и compilation. Завершить начатый batch.
После подготовки обновить old_value/advantages, не меняя actions/logp;
временный optimizer отбросить, PPO Adam начинает с первого шага.

Показать MSE/EV до и после и MSE постоянного среднего return по тем же
позициям. Это диагностика качества critic, без новой кампании его подбора.
Первые обычные rollout покажут реальную частоту побед на training;
10,16% development заранее переносить на них нельзя.

Сохранить принятые правила активного времени, последнего уменьшенного
rollout, завершения начатой попытки с KL/rollback и возобновления. Collection,
critic, compilation, PPO/KL и сохранения входят в 7200 секунд; боевая оценка
учитывается отдельно. Последнюю начатую волну/эпизоды завершить, превышение
решений записать. Не начинать новый сбор или попытку после границы.

Пять последовательных rollout без побед — остановка до PPO пятого;
три rollout без принятого PPO-шага — прежняя отдельная остановка.

## Оценки и решение

Прежние 128 development случаев, argmax против CP, CPU / 4 workers:
ноль, 262144, 524288, 1048576 и 2097152 новых решений, на границе rollout.
Текущий baseline 27/33/68 можно переиспользовать при неизменных evaluator
и платформе; при переходе на другую платформу оценить родителя один раз.

После точки 524288, если ни один новый checkpoint не превысил число побед
родителя, остановиться с `no_development_gain`. Это экономическая граница,
а не доказательство невозможности позднего улучшения. При улучшении идти
до согласованного бюджета. Не требовать положительного CI на промежуточных
development оценках. При остановке оценить последние изменившиеся веса,
если их ещё не оценивали.

Выбор — максимум development argmax wins, при равенстве раньше; BC участвует.
Если выбран BC, additional не запускать. Иначе прежние 256 additional
случаев для кандидата и родителя одним evaluator; совместимый BC результат
45/71/140 переиспользовать, при необходимости переоценить. Paired bootstrap
10000, seed 20261103, parent-world. Положительная нижняя граница CI
поддерживает полезность продолжения; это validation, не независимый test.

Sampling отслеживать по штатному training; отдельная sampling-кампания не
нужна. Отчёт показывает argmax-кривую, sampling W/D/L, critic, KL/откаты,
срезы карт/армий/стартов/сторон и фактический бюджет. Минимум результата —
понять, даёт ли PPO прирост после восстановления успешных траекторий.

Результаты разместить в `artifacts/rl/ppo-target-bc-t05/`. Достаточны
существующие checkpoints/метрики и короткая конфигурация с родителем,
случаями, seed и T. Не добавлять новую систему паспортов. Не запускать
параллельно BC, новые температуры/seeds, другую награду или закрытый test.

## Исполнение

Температура задаётся `policy_temperature` (по умолчанию 1); фиксированный
профиль `configs/rl-ppo-target-bc-t05.json` устанавливает 0,5. В rollout
сохраняется та же температура; PPO/replay отклоняют несовпадение. Behavior
log-probabilities уже описывают распределение при T и повторно не масштабируются.

Локальная проверка одного полного обновления сохраняется отдельно:

```powershell
.venv/Scripts/python.exe tools/run_ppo.py run --config configs/rl-ppo-target-bc-t05.json --out artifacts/rl/ppo-target-bc-t05-local-check --runtime-config artifacts/rl/ppo-target-bc-t05-launch/local-runtime.json --device cuda --max-updates 1
```

`--max-updates` — операционная пауза на сохранённой границе без изменения
исследовательского бюджета и без additional. Проверочная локальная работа
не переносится в основной опыт. Основной Linux/CUDA-запуск начинает с BC
и пустого Adam, без `--max-updates` и без `--out`, используя подтверждённый
runtime из ограниченного профилирования той машины.
