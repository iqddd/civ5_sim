# RL-01: спецификация первого обучаемого тактического агента

Версия: 1.4. Дата: 4 ноября 2026 года. Статус: реализация проходит техническую
приёмку; результаты обучения публикуются отдельно в `artifacts/rl`.
Числовая конфигурация: [configs/rl-v1.json](../configs/rl-v1.json).

## 1. Результат и границы этапа

Получить компактного агента, который управляет всей армией по одной команде,
играет при тумане войны, использует историю наблюдений и превосходит greedy
на незнакомых картах. Отдельно измерить пользу явной памяти контактов и GRU.
Успех против random — проверка обучения, но не завершение этапа.

Исходные требования: [conversation.md](../conversation.md) и
[role_for_civ5_agent.md](../role_for_civ5_agent.md). Архитектура и числа ниже —
выбранная отправная точка, а не уже подтверждённые экспериментом оптимумы.

| Свойство | RL-01 |
|---|---|
| Управление | Одна армия; одна допустимая команда за решение |
| Карта | Известна целиком; 10×10, 12×12 и 16×16, без wrap |
| Информация о враге | Известен стартовый состав; текущие позиции только в обзоре |
| Типы | warrior, archer, chariot_archer, spearman, horseman |
| Численность | 2–5 на сторону при обучении; интерфейс до 8 |
| Правила | Существующий профиль CP Only; туман и случайный урон включены |
| Победа | Полное уничтожение армии; лимит раундов даёт ничью |
| Управление риском | Один профиль: максимизировать вероятность победы минус поражения |
| Обучение | С нуля; episodic recurrent PPO |
| Память | Наблюдаемые контакты + GRU; отдельные контрольные варианты |
| Соперники в базовом обучении | random и greedy, зафиксированные версии |
| Не входят в базовый запуск | CP как учитель, self-play, поиск модели, belief loss, privileged critic |

Потери армии — важная дополнительная метрика, но не отдельная награда в v1.
Это сознательно допускает победы с тяжёлыми потерями. Другой приоритет требует
новой версии цели, а не незаметного изменения коэффициентов.

## 2. Что уже есть и что требуется добавить

Использовать `Battle.observe`, `available_actions`/`action_buffer`, `step`,
`step_batch`, `reset`, существующую логику исходов и штатный просмотрщик.
`observation_buffer` и `action_buffer` переиспользуют память: сборщик обязан
копировать нужные данные до следующего вызова. Нельзя сохранять ссылки на
перезаписываемые ctypes-буферы.

`run_match` остаётся эталоном исполнения и оценки. Для обучения нужен отдельный
сборщик с `Battle(log=False)`: штатный `run_match` пишет полный журнал и снимки
на каждом шаге, что не требуется для миллионов решений. Правила завершения
необходимо вынести в общий компонент либо проверить дифференциально с `run_match`.

Новые компоненты и предлагаемые пути:

| Путь | Ответственность |
|---|---|
| `civ5rl/observation.py` | Публичные признаки и память контактов |
| `civ5rl/model.py` | Пространственный энкодер, GRU, policy/value |
| `civ5rl/env.py` | Переход от решения обучаемой стороны до следующего её решения |
| `civ5rl/collector.py` | Независимые бои, пакетный inference, завершённые эпизоды |
| `civ5rl/ppo.py` | Returns, последовательности, loss, обновления |
| `civ5rl/corpus.py` | Корпус, разделение миров, расстановки, манифесты |
| `civ5rl/checkpoint.py` | Воспроизводимое сохранение/возобновление |
| `civ5rl/agent.py` | Обычный интерфейс `reset(context)` / `act(observation, actions)` |
| `tools/train_rl.py` | Обучение и продолжение |
| `tools/evaluate_rl.py` | Сравнение, доверительные интервалы, реплеи |
| `tools/benchmark_rl.py` | Скорость полного цикла и память |

Эти пути — план реализации, не существующие команды. Тренировочный интерфейс
не должен выдавать модели `PlanningServices`, `Battle`, snapshot, RNG или seed.

## 3. Информационный контракт

### 3.1. Разрешено

Ландшафт, реки, геометрия; свои текущие юниты; видимые враги и их публичные
поля; текущая маска обзора; счётчик завершённых ходов сторон; начальные составы;
лимит раундов; свои ранее выбранные команды; сведения, сохранённые из собственных
прошлых наблюдений. Отложенная видимость до конца хода берётся из ядра как есть.

### 3.2. Запрещено

Истинные скрытые координаты, HP и смерти; остаток движения и приватные флаги
врага; память противника; его команды между нашими решениями; скрытая история
полученного им урона; реальный RNG; параметры размещения; исходный seed;
`spawn_candidates`; metadata карты; идентификатор сценария/соперника;
значения CP danger и результаты привилегированных ветвей поиска.

Награда и учебные метки не поступают на вход policy. В v1 не передавать
`StepResult` целиком: информация для решения получается из нового наблюдения
и собственной прошлой команды. Конечный исход используется только обучением.

Пара состояний с одинаковой публичной историей должна давать одинаковые
признаки, память и распределение команд, даже если скрытые позиции различаются.
Это условие распространяется на состав **и порядок** списка команд.

### 3.3. Явная память контактов

Хранить словарь по ID ранее виденного врага: тип, последняя клетка, последние
наблюдаемые HP, номер завершённого хода противника при наблюдении. При повторном
обнаружении обновлять запись. ID служит только для сопоставления наблюдений;
сырой номер ID не является числовым признаком сети.

В текущие каналы врага включать только видимых. Остальные записи — устаревшие
контакты; не перемещать их по истинному состоянию и не удалять по скрытой смерти.
В v1 исчезновение даже после нашей атаки не превращается автоматически в
«подтверждённое убийство»: это упрощение обработки событий, а не утверждение,
что враг жив. Запись остаётся последним наблюдением и удаляется при reset.
Новая видимость пустой клетки не стирает исторический факт: пустота видна в
текущих каналах, а контакт помечен как устаревший.

Возраст — число прошедших **ходов противника**, а не число наших команд.
При стандартном старте стороной 0 и публичном `turn=t` в момент нашего решения
для стороны `p` это `enemy_clock=floor((t+p)/2)`. Возраст контакта — разность
таких часов; проверять формулу на обеих сторонах. Внутри словаря возраст точный;
в признаках ограничен 32. Предыстория за границами этого диапазона доступна GRU.

## 4. Входные тензоры

Обозначения: `N=width*height <= 256`, `B` — число независимых состояний,
`A` — число предложенных команд. Собственная сторона всегда кодируется как
«своя», но карту не отражать и не вращать. Соседство строится через
`civ5map.maps.adjacent`, с учётом `row_parity`; квадратная свёртка не используется.

### 4.1. Клетки: `[B, N, 73]`, float32

| Поля, в порядке конкатенации | Каналов | Кодирование |
|---|---:|---|
| terrain | 7 | one-hot в порядке `engine.TERRAINS` |
| elevation | 4 | one-hot в порядке `engine.ELEVATIONS` |
| feature | 9 | one-hot в порядке `engine.FEATURES`, включая None |
| Реки по шести рёбрам | 6 | 0/1; раскрыть владельцев рёбер и boundary_rivers |
| Существование соседа по шести направлениям | 6 | 0/1; порядок направлений `adjacent` |
| x, y | 2 | `2*x/(width-1)-1`, аналогично y |
| Проходимость | 1 | Публичная проходимость для поддерживаемых наземных типов |
| Текущий обзор | 1 | Маска ядра |
| Возраст последнего обзора | 1 | `min(age,32)/32`; 1, если никогда не видели |
| Когда-либо видели клетку | 1 | 0/1, только реальные полученные наблюдения |
| Тип своего юнита | 5 | one-hot, нули при отсутствии |
| Состояние своего юнита | 8 | HP/100, moves/240, attacked, acted, fortified, waiting, два счётчика урона/100 |
| Тип видимого врага | 5 | one-hot, нули при отсутствии |
| Состояние видимого врага | 2 | HP/100, fortified |
| Число устаревших контактов каждого типа на клетке | 5 | count/8 |
| Возраст самого свежего устаревшего контакта каждого типа | 5 | `min(age,32)/32`; 0, если контактов нет |
| Средние последние HP устаревших контактов каждого типа | 5 | mean(HP)/100; 0, если контактов нет |
| **Итого** | **73** | |

Счётчики своего урона ограничивать [0,1] после деления; остальные перечисленные
нормировки фиксированы, running normalization отсутствует. На одной клетке
могут накапливаться несколько исторических контактов: это не текущая занятость.
Видимые контакты исключаются из исторических 15 каналов, но остаются в словаре.
Неизвестный enum — ошибка schema, не молчаливое преобразование в None.

### 4.2. Общие признаки: `[B,33]`

Пять векторов по 5 типов, каждый с делением на 8: начальный свой состав,
начальный вражеский состав, текущие живые свои, текущие видимые враги,
число когда-либо виденных различных врагов. Последнее не равно числу живых.

Остальные 8 скаляров, в данном порядке:

1. `turn/(2*max_rounds)`.
2. Число ходов противника после прошлого нашего наблюдения, min(число,32)/32.
3. Начало нового собственного хода (включая первый вызов).
4. width/16.
5. height/16.
6. Мы начинающая сторона (side==0).
7. random_damage (в основном эксперименте всегда 1).
8. max_rounds/60.

На первом наблюдении возраст из пункта 2 считается от старта матча; у стороны
1 уже мог пройти один ход противника. Ни один счётчик не извлекается из snapshot.

### 4.3. Предыдущая собственная команда: `[B,20]`

8 one-hot значений: семь `engine.KINDS` и START; 6 значений типа исполнявшего
юнита (пять типов и NONE); x/y клетки источника и x/y цели в нормировке выше;
два бита наличия источника и цели. Итого 8+6+4+2=20.
Источник запоминается **до** исполнения команды, цель — приказанная, даже если
движение прервалось контактом. Для отсутствующих клеток координаты нулевые.
У end_turn источник/цель отсутствуют. У fortify/skip источник есть, цели нет.

### 4.4. Переменные размеры

Клетки дополняются до размера максимальной карты в minibatch; `cell_mask`
исключает padding из pooling, loss и соседства. Команды хранятся ragged либо с
маской padding. Поддержать произвольное число допустимых команд в пределах
ядра: запрещены молчаливое усечение, top-k CP и отбор по истинной опасности.

## 5. Архитектура: HexEncoder + GRU + action scorer

Выбран небольшой направленный графовый энкодер гексов. Он явно использует
шесть соседей, сохраняет реки и местность и не требует полного attention между
клетками на каждом шаге длинной последовательности. Это архитектурный выбор
для первого опыта, а не результат сравнения с Transformer.

### 5.1. Пространственный энкодер

Проекция `Linear(73,128)`, GELU. Затем четыре независимых residual-блока:

```text
m_i = GELU(LayerNorm(W0*x_i + sum_d(W[d+1]*x_neighbor(i,d)) + b))
u_i = x_i + m_i
x_i_next = u_i + Linear(256,128)(GELU(Linear(128,256)(LayerNorm(u_i))))
```

Семь матриц 128×128, общий bias 128 в первом выражении; у двух Linear MLP
есть bias. Отсутствующий сосед даёт ноль. Все LayerNorm имеют affine-параметры
и eps=1e-5. Нет BatchNorm, dropout и embedding абсолютного tile ID.
Выход `e_i` имеет ширину 128. Радиус прямого пространственного обмена — 4 гекса;
это ограничение первой архитектуры. Глобальный pooling видит всю карту,
но не заменяет детальное пространственное планирование на больших дистанциях.

### 5.2. Контекст и память

`concat(masked_mean(e), masked_max(e), globals33, previous_action20)`:
256+33+20=309 значений. MLP `309→256→256`, GELU после каждого слоя.
Затем однонаправленная однослойная `GRU(input_size=256, hidden_size=256)`.
`h_init=0`; одна память на армию, а не на каждого юнита. Скрытое состояние
сохраняется между собственными ходами. На ходе противника GRU не вызывается:
следующий вход показывает последствия, доступные при следующем решении.

### 5.3. Политика

Сеть выдаёт оценку каждой команды из публичного списка. Для команды собрать:

- `h_t`: 256;
- `e_source`, `e_target`: по 128, нули для отсутствующих клеток;
- kind: one-hot 7;
- тип исполнителя: one-hot 5, нули у end_turn;
- `(target_x-source_x)/15`, `(target_y-source_y)/15`: 2;
- гексагональное расстояние/32: 1;
- наличие источника и цели: 2.

Всего 529. Если одной из клеток нет, относительные координаты и расстояние
равны нулю. Расстояние вычисляется по геометрии гексов с row_parity, без
учёта занятости и скрытых юнитов. Для swap target — клетка партнёра.
MLP `529→128→1`, GELU между слоями. Один softmax по всем допустимым командам;
нет независимого выбора команды для каждого юнита.

Сортировать команды по `(kind_index, unit_id, target_tile)` до формирования
распределения; удалить точные дубликаты с диагностикой нарушения контракта.
Веса разделяются между командами, номера списка не имеют embedding.
Padding logits = -inf; log_softmax, entropy и categorical sampling — float32.

Обучение и основной тест: categorical sampling, temperature=1.
Просмотр детерминированной игры: argmax с первым элементом при точном равенстве;
это отдельный режим оценки, его результаты не смешиваются с основными.

### 5.4. Critic и размер

`V(h_t)`: MLP `256→128→1`, GELU, линейный выход без tanh. Он предсказывает
исход именно нашей ограниченно информированной политики. Энкодер и GRU общие
с actor, градиент value loss проходит в них. Истинное состояние не используется.

При описанных bias и стандартной GRU PyTorch — **1 375 362 параметра**
в базовой модели; число проверено независимым подсчётом модулей PyTorch.
Объём весов float32 — около 5,25 MiB; основная память обучения потребуется
для активаций и данных.
Это не замер VRAM и не обещание скорости.

Инициализация: Xavier uniform для обычных Linear и W направлений, bias=0;
LayerNorm weight=1/bias=0; GRU input-матрицы Xavier, каждая из трёх recurrent
матриц ортогональная, оба bias=0. Последний Linear policy: orthogonal gain=0.01;
последний Linear value: orthogonal gain=1.0. Dropout отсутствует и при обучении.

## 6. Переход среды и исходы

Один переход обучаемой стороны начинается перед её командой. Если она не
завершила ход, следующий вход — сразу после команды. Если выполнила end_turn,
сборщик исполняет все команды фиксированного соперника до следующего решения
обучаемой стороны либо завершения боя. Урон/гибель на ходе врага относятся к
предшествующему переходу обучаемой стороны. Перспектива reward не меняется.

В одном тренировочном матче обучается одна сторона; другая — frozen opponent.
Сторона learner выбирается 50/50. При старте learner за сторону 1 сначала
исполнить соперника. Матч, закончившийся до первого решения learner, учитывать
в результатах и диагностике, но он не создаёт policy-переходов.

| Событие | reward | Terminal |
|---|---:|---|
| Бой продолжается | 0 | false |
| Победа learner | +1 | true |
| Поражение learner | -1 | true |
| Взаимное уничтожение / лимит раундов | 0 | true |

Лимит раундов — правило игры с ничьёй, поэтому bootstrap после него равен нулю.
Уничтожение проверяется раньше лимита, как сейчас в `run_match`.
Ни награды за урон/убийство/обзор, ни штрафа за команду, ни награды за HP нет.
`gamma=1` не делает раннюю победу ценнее поздней; длительность показывается
отдельно. Модель может выбрать спасительную ничью вместо вероятного поражения.

Технический лимит — 2000 вызовов на ход стороны, как в текущем AI-стенде.
Превышение, illegal action, exception, NaN и таймаут — **ошибки**, не поражение
и не ничья. Сохранить воспроизведение и остановить сбор текущего update.
Нельзя молча выкидывать неудачные эпизоды или принудительно вставлять end_turn.

## 7. PPO, returns и последовательности

### 7.1. Только завершённые эпизоды

На время сбора замораживаются веса learner и версии соперников. Цель — не менее
8192 решений learner на update. Сбор идёт волнами по 32 заранее назначенных
episode IDs: каждый слот исполняет один полный бой, завершившийся слот ждёт
остальные. После завершения волны, если цель ещё не достигнута, начинать
следующую волну. Иначе завершить rollout. Все переходы всех волн входят в update,
поэтому его реальный размер может превышать 8192. Не отбрасывать длинные бои
ради размера. Записывать размер превышения, время ожидания слотов и длины боёв.
Если целая волна не создала ни одного решения learner, остановиться с ошибкой
корпуса. Такой режим жертвует частью загрузки CPU ради простого точного повторения.

После update все среды начинают новые бои с нулевой памятью. Так не переносится
скрытое состояние старых весов в сбор новым actor. Старые траектории не
подмешиваются в будущие PPO updates; архив реплеев не является replay buffer PPO.

### 7.2. Targets

`gamma=1`, `lambda=1`; в этой версии GAE эквивалентен Monte Carlo return:
`G_t = итог боя` для каждого решения эпизода. `A_t=G_t-V_old(history_t)`.
Сначала вычислить все targets замороженными старыми значениями. Advantage
нормировать один раз по всем реальным переходам update: `(A-mean)/(std+1e-8)`.
Returns не нормировать; rewards не масштабировать. Padding в статистики не входит.

Это простой, шумный сигнал. Отсутствие ослабления далёкой награды дисконтированием
не означает, что GRU получает градиент через всю историю: это определяется
длиной BPTT ниже. Большая доля ничьих может означать отсутствие полезного сигнала.

### 7.3. Loss

Для старой вероятности сохранённой команды `logp_old` и новой `logp`:

```text
ratio = exp(logp - logp_old)
L_policy = -mean(min(ratio*A, clip(ratio, 0.8, 1.2)*A))
L_value = mean((V-G)^2)
H_norm = H(policy)/log(number_of_actions)  # 0, если действий ровно одно
L = L_policy + 0.5*L_value - entropy_coef*mean(H_norm)
```

Здесь `L_value` уже определён без множителя 1/2: второй раз его не добавлять.
В baseline `belief_coef=0`. Actor и critic оптимизируются одним Adam.
В среднем участвуют реальные обучаемые позиции, не префиксы восстановления
памяти и не padding. Нормированная entropy выбрана, чтобы масштаб регуляризации
меньше зависел от числа доступных перемещений; это вариант PPO для проекта.

### 7.4. Восстановление recurrent state

Разбить каждый эпизод на последовательные неперекрывающиеся chunks до 128
решений. Каждый переход участвует в loss ровно один раз за PPO epoch.
Перемешивать chunks, но не шаги внутри них. Начальный hidden state для chunk
получать **пересчётом всего предшествующего префикса этого эпизода от h=0
текущими весами, без градиента**, затем detach. На самих 128 шагах — BPTT.

Пересчёт делать перед соответствующим minibatch, а не один раз на все epochs:
после optimizer.step веса меняются. Старый rollout hidden state сохранять для
диагностики, но не использовать как точное новое состояние. Префиксы можно
пакетировать; кешировать их выходы разрешено только пока веса неизменны.

Это вычислительно дороже короткого burn-in, зато исключает отдельную
аппроксимацию устаревшей памяти. Профилировать стоимость. Переход на burn-in=64
со старым начальным hidden возможен лишь отдельной абляцией с измерением ошибки,
не как незадокументированная оптимизация.

### 7.5. Minibatch и контроль шага

Один optimizer minibatch — 8 chunks, максимум 1024 loss-позиции. На 4060 Ti
исполнять microbatch по 1 chunk с gradient accumulation до 8. Масштаб каждого
microbatch пропорционален числу реальных loss-позиций, чтобы padding не менял
веса. Последний minibatch epoch может быть меньше. На 5090 увеличить только
microbatch до 2 или 4 после проверки памяти; математический minibatch сохраняется.

Четыре PPO epochs. После каждой эпохи пересчитать mean approximate KL по всем
loss-позициям rollout с последовательным прогоном текущей policy:
`mean(exp(logp-logp_old)-1-(logp-logp_old))`.
Если KL > 0.015, следующие epochs этого update не выполнять. Это мягкий
контроль, не гарантия и не откат уже исполненной эпохи. Логировать clip fraction.
Проверить `ratio≈1`, `KL≈0` до первого обновления на том же rollout.

## 9. Корпус и curriculum

### 9.1. Разделение миров

64 исходных мира train, 16 validation, 32 test. World seeds: соответственно
10000…10063, 20000…20015, 30000…30031. Резерв для неконструируемых миров:
продолжать соответствующий диапазон, не переходя в диапазон другого split;
каждый отказ записывать. Зафиксировать конфигурацию генератора как
`corpus-generation-v1.json`: Pangaea, standard. Существующий CLI принимает
`--world-size 3 --age 2 --temperature 2 --rainfall 2 --sea-level 2 --count 4`;
пятый элемент options в текущем `generate` фиксирован как 2. Путь к игре,
seed и out задаются явно для каждого мира. Это проверено по `civ5map/__main__.py`.

С каждого мира отбирать четыре 16×16 участка штатным фильтром. Для 10×10
и 12×12 отбирать по четыре участка с теми же требованиями связности и места
под армии; для этого потребуется расширить подготовку корпуса, стандартный
`generate` CLI сейчас отбирает 16×16.
Все размеры и перекрывающиеся вырезки одного мира остаются в его split.
До начала обучения сохранить точные JSON карт, хеши, координаты вырезок,
генератор и происхождение. Недобор карт — явная ошибка подготовки корпуса.

Старые карты из ручной разработки, включая pangaea-42, не объявлять новым
слепым test. Их можно оставить для отладки и иллюстраций.

### 9.2. Составы и размещение

Стартовые армии симметричны по составу, HP=100, состояния и движения штатные.
Стороны различаются расположением и очередностью. Для n≥3 обязательно хотя бы
один ближний тип и один стрелковый. Сэмплировать n типов равномерно из пяти
с возвратом, отклоняя несоответствующие составы. Для n=2 применять то же условие.
Это условное равномерное распределение допустимых упорядоченных составов.

Два режима размещения:

- **contact**: выбрать две проходимые клетки на расстоянии 2; разместить по
  одной единице каждой стороны на них, остальных — без наложений в радиусе 2
  от своей опорной клетки в общей связной области. Проверить, что обе стороны
  реально видят хотя бы одного врага по правилам ядра. Выбор клеток/юнитов
  равномерный из соответствующих кандидатов; неудачу повторить до 100 раз,
  затем сообщить ошибку подготовки сценария.
- **separated**: штатное размещение в двух `spawn_candidates`, дополнительно
  отклонять расстановку с начальным контактом хотя бы для одной стороны.
  До 100 попыток на карту/состав, затем выбрать следующую карту с записью
  отказа; не подменять молча на contact.

Часть close-contact боёв нужна для раннего сигнала от атак и исходов; туман
во всех случаях остаётся включён. Разные позиции могут становиться скрытыми
в ходе самого боя. Армии разной начальной силы — последующее расширение,
отдельно от данного подтверждающего набора.

### 9.3. Расписание

Границы измеряются решениями learner, не командами обеих армий. Стадия и смесь
фиксируются при начале rollout; внутри update не меняются.

| Диапазон | Карта; армии; max_rounds | contact / separated | random / greedy |
|---|---|---|---|
| 0…250 тыс. | 10×10; 2×2; 20 | 50% / 50% | 50% / 50% |
| 250 тыс.…1 млн | 12×12; 3×3; 30 | 30% / 70% | 25% / 75% |
| 1…2 млн | 16×16; n равномерно 3…5; 40 | 20% / 80% | 10% / 90% |
| 2…10 млн | 16×16; n равномерно 3…5; 60 | 20% / 80% | 10% / 90% |

Validation/test основной задачи: 16×16, n=3…5, 60 раундов, **separated**,
random_damage=true, fog=true. Отдельный малый набор всех учебных стадий нужен
для диагностики забывания; его не смешивать с основной метрикой.

Расписание фиксировано для сопоставимости. Если на первой стадии за 250 тыс.
решений победы не растут и почти все бои ничейные, сначала диагностировать
достижимость контакта, mask, значения reward и выбор end_turn. Затем создавать
новую версию curriculum, не продлевать каждый seed по произвольному правилу.

## 10. Оценка и проверка памяти

### 10.1. Парные игры

Каждая тестовая расстановка проигрывается дважды: learner управляет стороной 0,
затем стороной 1; физическая начальная расстановка и составы сохранены.
Это одновременно усредняет расположение и преимущество первого хода. Карты
не отражать без отдельного корректного преобразования рек и row_parity.
Боевой seed в паре одинаков; из-за разных действий это не гарантирует
одинаковую последовательность соответствующих атак и не считается ею.

Для воспроизводимости manifest разделяет seeds карты, расстановки, боя,
policy sampling и выбора соперника. Оценка не расходует тренировочный RNG.

Производные seeds получать как первые 16 hex-цифр SHA-256 канонического JSON
`{schema:1, namespace, master_seed, episode_id, stream, side}`: UTF-8,
`sort_keys=True`, `separators=(',',':')`. Число uint64; для библиотеки с меньшим
диапазоном явно записать `seed % 2**32`. Namespace различает train/validation/
test/diagnostic; stream — placement/battle/opponent/learner_sampling/roster/map.
Master seeds manifest: train — training seed, validation — 20261104,
test — 20261105, diagnostic-test — 20261106. Training seed не влияет на
расстановки validation/test. Seed исходного мира задаётся отдельно разделом 9.
В парной оценке `episode_id` для placement/battle/roster/map — общий ID случая,
а `side=-1`: смена стороны learner или соперника не меняет начальную расстановку
и боевой seed. Для sampling и opponent `side` — физическая сторона 0/1.
Для policy sampling применять независимый генератор на episode/side; глобальный
categorical RNG на GPU не должен связывать результат боя с размером batch.
Reference допускает CPU float32 sampling из переданных вероятностей; оптимизация
этого места требует сохранения распределения и фиксированного протокола RNG.

Validation: 16 миров × 4 расстановки = 64 случая; по две стороны и два
соперника = 256 матчей на checkpoint. Test: 32 мира × 8 расстановок = 256
случаев; две стороны и два соперника = 1024 матча на training seed.
После трёх seeds — 3072 основных тестовых матча на вариант модели.

Выбор checkpoint отдельно для каждого training seed: максимальный validation
score против greedy; при равенстве выбрать более ранний. Основной test
открывается только для заранее выбранных checkpoints и вариантов. После
настройки по test этот набор становится development; для нового подтверждения
требуется новый независимый test manifest.

**В pilot финальные test-наборы остаются закрытыми.** Это относится к основным
боям, test-сценариям памяти и CP-стресс-тесту на test-картах. Pilot использует
только validation и dev-сценарии памяти; его отчёт и показательные реплеи
выбираются из этих наборов. По ним разрешено менять архитектуру, curriculum
и гиперпараметры. Просмотр test-боёв для поиска ошибок поведения тоже считается
использованием test и в pilot не допускается.

До открытия test сохранить неизменяемый план финальной оценки: варианты A/B/C,
training seeds, хеши выбранных по validation checkpoints, конфигурации,
манифесты, бюджеты, метрики, основные сравнения и критерии приёмки. После этого
выполнить запланированную оценку всех выбранных вариантов, включая неудачные
результаты. Новые настройки и выбор checkpoint по результатам test запрещены
в рамках того же подтверждающего эксперимента.

Закрытость — ограничение использования результатов, а не секретность seeds.
Заранее допустимы генерация, сохранение и автоматическая проверка структуры,
разделения миров и корректности test-корпуса, без запуска оцениваемых моделей,
тактического просмотра и обратной связи для настройки. Исполняемая оценка
pilot должна отклонять запрос split=test или diagnostic-test явной ошибкой.

### 10.2. Метрики

Основная: `score=(wins+0.5*draws)/games`, при нулевых технических ошибках.
Обязательно рядом показывать W/D/L, обе стороны отдельно и число матчей.
Поскольку E[reward]=2*score-1, score согласован с выбранной терминальной целью.
Ошибки приводят к неполной/проваленной оценке; их не исключать из знаменателя
ради красивого результата и не интерпретировать как игровой исход.

Дополнительно: выжившие и HP каждой стороны; длительность в раундах и командах;
доля ничьих по лимиту; время до первого контакта; причины завершения;
latency inference p50/p95; полный wall time; peak VRAM и RAM.
Урон/HP из полной информации можно использовать для отчёта, но не входов actor.

95% интервалы: 10 000 парных bootstrap-выборок с фиксированным seed 20261103.
Для одного обучения ресэмплировать **миры**, сохраняя вместе вырезки, обе стороны
и matched outcomes сравниваемых моделей. Для итогового среднего трёх обучений
дополнительно ресэмплировать training seeds, а миры выбирать общими для них.
Отдельно публиковать результаты всех трёх seeds: три обучения дают ограниченную
оценку межзапускового разброса, даже при тысячах матчей.

### 10.3. Контрольные варианты

| Вариант | Что получает | Что проверяет |
|---|---|---|
| A: current-only | Текущие наблюдения, без исторических каналов и GRU | База без накопленной памяти |
| B: contacts-MLP | Все публичные признаки и явная память, без GRU | Достаточность инженерной памяти |
| C: contacts-GRU | Полная базовая спецификация | Добавочная польза обучаемой памяти |
| D: C + belief | Только после A/B/C | Польза вспомогательных меток |

В A занулить 15 каналов контактов, канал возраста обзора и «когда-либо видели»;
в globals занулить ever-seen counts; previous_action заменить START при каждом
решении, delta enemy clock и начало нового хода — занулить. Текущее время,
составы, текущий обзор и собственные текущие флаги сохраняются. Текущее состояние
само содержит легальные следы прошлого; их не нужно искусственно удалять.

В A/B вместо GRU использовать MLP `256→768→256`, GELU после каждого слоя.
Это 394 240 параметров против 394 752 у GRU; размер почти одинаков, но FLOPs
и wall time всё равно публикуются. Все варианты используют ту же policy/value
голову и общий бюджет собственных решений; B отличается от C только блоком памяти.
A/B могут считать куски параллельно, не притворяясь рекуррентными.

### 10.4. Диагностические истории

Сделать отдельные train/dev и test семейства ситуаций: потеря контакта на
развилке, угроза скрытого конника лучнику, обход укрытия, разведка перед вводом
основной армии. В первом этапе это диагностика; не награждать специально
заранее выбранное действие и не включать её результаты в reward.

Для test: 32 независимые геометрии × 4 пары историй = 128 пар, каждая история
играется за обе стороны, всего 512 продолжений на модель и training seed.
Пары должны быть достижимы правилами ядра, иметь одинаковое текущее **сырое**
наблюдение и допустимые команды, но разные ранее полученные сведения.
Исторические каналы B/C закономерно могут отличаться. Проверять равенство
сырых входов автоматически, не по визуальному сходству картинок.

Префикс воспроизводится как наблюдения и собственные заранее записанные команды;
память модели проходит его обычным порядком. Loss на навязанных командах нет,
оценка начинается только в точке свободного выбора и идёт до исхода боя.
Скрытые положения в двух вариантах могут различаться в соответствии с их
историей; их нельзя показывать модели. «Правильность» проверяется исходами
продолжений против фиксированного соперника, а не совпадением с одной разметкой.

Для различения B/C включить часть историй с одинаковыми последними контактами,
но различным порядком/маршрутом прошлых наблюдений. Должно существовать
проверяемое различие в полезных действиях; если B уже достаточно для задачи,
не объявлять отсутствие прироста C ошибкой эксперимента.

Основное свидетельство пользы истории — B или C лучше A. Прирост C над B
отвечает более узкому вопросу о пользе GRU поверх явной памяти. Обнуление h
во время игры обученного C — дополнительная диагностика со сдвигом входного
распределения, не замена независимому обучению A/B.

### 10.5. CP

В текущем [контракте CP](combat-ai-contract.md) `privileged_cp_queries=true` —
единственный реализованный профиль. Ветви могут получать истинные текущие
координаты врага из активной памяти и новые контакты при гипотетическом обзоре.
Поэтому baseline не копирует CP-команды и не использует CP как источник признаков.

После выбора модели отдельный стресс-тест: первые 64 случая test по manifest,
две стороны, 128 матчей на seed против CP. Указать версию, бюджеты поиска,
привилегии и wall time. Эти результаты не смешиваются с проверкой равных
информационных условий. Победа над CP не является критерием приёмки RL-01.

## 11. Вспомогательная belief-head: спецификация отдельной абляции

По умолчанию выключена. Для D добавить к каждому `concat(e_i,h_t)` ширины
384 MLP `384→128→6`, GELU. Выход — категориальное распределение:
клетка пуста от врага или на ней враг одного из пяти типов. Учебная метка
берётся из истинного состояния **в момент соответствующего наблюдения**.
Голова не предсказывает одну гарантированно правильную скрытую расстановку.

Loss — обычная невзвешенная cross-entropy по скрытым проходимым клеткам,
сначала среднее по клеткам каждого решения, затем по решениям, где такие клетки
есть. При их отсутствии contribution=0. Padding и видимые клетки исключаются.
`L_total += 0.1*L_belief`; градиент поступает в encoder/GRU. Class weights и
focal loss не использовать: они меняют смысл вероятностей без коррекции.
Из-за преобладания пустых клеток одной accuracy недостаточно.

Предсказания belief не подаются обратно actor в v1-D: влияние только через
общее обучение представления. Отдельный канал labels физически не входит
в forward policy. Голова и labels не нужны для игры после обучения.

Оценивать NLL, Brier score, калибровку occupancy, recall/top-k на непустых
клетках и ожидаемое число скрытых врагов. Отдельно сравнивать с простым prior
по составам/проходимым клеткам. Не менять coefficient после просмотра test.
Проба коэффициентов 0.03/0.1/0.3 допустима только на train/validation отдельными
экспериментами с отчётом дополнительных затрат.

## 12. Ресурсы, окружение и хранение

Оптимизация исполнения v1.2: PPO minibatch по-прежнему равен 8 chunks / максимум
1024 loss-позициям. В FP32-пробе выбран microbatch=4; после перехода на BF16
v1.3 использует microbatch=8 по замеру скорости и VRAM на 4060 Ti.
GRU обрабатывает несколько независимых последовательностей с padding, который
не входит в loss; их hidden states и полные префиксы остаются раздельными.
Публичный rollout переносится в VRAM один раз на update, включая targets и old
logp; повторные epochs и prefix replay используют GPU-resident данные.
Spatial encoder и action/value heads компилируются `torch.compile(dynamic=True)`,
GRU остаётся штатной cuDNN GRU. Attention отсутствует. TF32 не включается.
По явному запросу пользователя v1.3 включает mixed precision BF16 для крупных
GEMM четырёх hex-блоков. Входная projection, сумма сообщений, context MLP и
policy/value heads остаются FP32: это уменьшает зависимость вероятностей от
размеров пошагового и пакетного исполнения. Веса, градиенты, Adam, GRU и её
hidden state остаются FP32. Log-softmax, entropy, PPO ratio,
returns/advantages и loss также FP32. GradScaler для BF16 не применяется.
Проверка неизменённых весов v1.4 сохраняет полные behavior log-probabilities
всех допустимых команд при реальном выборе, вместе с прежним выбранным old_logp.
Они не заменяются результатом replay. Выбранное значение должно точно совпадать
с соответствующим элементом записанного распределения; вероятности нормированы.
В BF16 проверяются средний полный categorical KL ≤1e-6 и максимальная total
variation по решениям ≤0.005 (TV = 0.5 × sum_a |p_a-q_a|). Метрики расстояния
вычисляются в float64 после повторной нормировки, чтобы не терять малый KL.
Max logp error остаётся диагностикой: относительная ошибка редкой команды сама
по себе не измеряет изменение всей политики. Дополнительно sampled approximate
KL ≤1e-6. FP32 сохраняет max logp error ≤0.001 и те же full-distribution guards.
Исторические offline rollouts без полного распределения допускаются только с
явно отключённым require_full_behavior_distribution и старым строгим max-bound;
новое BF16-обучение требует полные distributions. NaN либо превышение любого
активного допуска — ошибка. Это контроль данных до PPO, не KL-stop обновления;
формулы loss и post-epoch sampled KL-stop не меняются.

Основание: в pilot update 14 независимый replay исходных inference batches
побитово воспроизвёл old_logp и hidden state. FP32 step-vs-sequence max logp
error 1.9e-6; в BF16 одна из 8724 выбранных команд имела ошибку 0.006882,
но mean full KL=4.60e-9, max TV=0.000705. Старый max-bound давал ложную остановку.
Побитовая идентичность разных batch shapes не гарантируется и PyTorch;
см. [Numerical accuracy](https://docs.pytorch.org/docs/2.15/notes/numerical_accuracy.html#batched-computations-or-slice-computations).
GRU имеет явный autocast-disabled регион: CUDA autocast RNN может выбирать
FP16 даже внутри BF16-контекста. Native BF16 support проверяется при запуске;
неподдерживаемый GPU даёт ошибку, а не незаметное переключение на FP16.
CUDA Adam использует fused backend; CPU reference остаётся eager.
Triton Windows зафиксирован в dependencies. Компиляция имеет отдельную холодную
стоимость; отчёты различают её и установившуюся скорость. Побитовая идентичность
CUDA eager/compiled не обещается: численные отклонения проверяются отдельно.
CPU exact-resume, правила, информационный контракт, reward, бюджет и формулы PPO
сохранены. Замена microbatch — изменение исполнения, а не размера optimizer step.
Пилот можно прервать через `tools/control_rl.py pause --out <run>`: файл
`stop.request` проверяется на границе завершённого update. Текущее обновление
заканчивается, атомарно сохраняются model/Adam/RNG/counters; новая validation
не начинается. Уже начатая validation завершается. Статус становится `paused`.
`tools/control_rl.py resume --out <run>` запускает продолжение в фоне из `latest`;
`status` показывает живой статус и последний checkpoint. OS file lock исключает
двух одновременных писателей. SIGINT/SIGBREAK также запрашивают мягкую остановку.
Для этой ревизии предусмотрен узкий `tools/archive/migrate_rl_audit.py`: он переносит
неизменённые model/Adam/RNG/counters в новый каталог с lineage и SHA256 родителя.
Разрешены только перечисленные изменения audit/telemetry и версии документа;
изменение модели, симулятора, корпуса, окружения, PPO или optimizer отклоняется.
Обычный resume по-прежнему требует точного совпадения passport. Файл
continuation.json позволяет control_rl.py управлять продолжением по прежнему пути.
После принудительного завершения процесса можно восстановить последний целый
checkpoint, потеряв незавершённый update. Полный CPU pause/resume проверяется
побитовым сравнением model/Adam/RNG с непрерывным обучением; для CUDA/compile
побитовая идентичность между разными формами вычисления не заявляется.
Внутренние снимки Battle разделяют принадлежащую Battle неизменяемую карту;
публичные snapshot/replay сохраняют независимые копии. Это устраняет глубокое
копирование ландшафта в каждой пробной ветви greedy без изменения его решений.

Проверено локально при подготовке: Windows, Python 3.13.9, PyTorch 2.15.0+cu132,
CUDA runtime 13.2, NumPy 2.5.4; `torch.cuda.is_available()=True`.
GPU RTX 4060 Ti 16380 MiB, драйвер 610.88; CPU i5-11600K (6/12), RAM около
31.9 GiB. Это проверка наличия, не проверка обучающего конвейера.

Создать отдельный lock обучения с этими версиями, Lupa и зависимостями,
зафиксировать URL/хеш PyTorch wheel. На другой машине выбрать совместимую
с GPU сборку, проверить небольшой forward/backward и записать отдельный паспорт;
версию окружения нельзя менять незаметно посреди сравнения.

Начать с 4 CPU workers по 8 сред. В worker ограничить численные библиотеки
одним CPU thread; GPU и модель принадлежат одному learner/inference процессу.
Windows multiprocessing — spawn с main guard. GPU batching объединяет запросы
готовых сред; шаги одной среды всегда последовательны. `step_batch` сам по себе
не означает исполнения всех боёв на разных CPU cores.

Reference: FP32, deterministic algorithms где поддерживаются, cuDNN benchmark
off, TF32 off, явные seeds Python/NumPy/Torch/CPU/CUDA. Неподдерживаемая
детерминированная операция — ошибка контрольного режима. [PyTorch не обещает
побитовую воспроизводимость между платформами и версиями](https://docs.pytorch.org/docs/2.15/notes/randomness.html).

Сборщик отправляет компактные CPU данные, не полные float32 карты 73 каналов
на каждый шаг: статический ландшафт общий, динамика компактная, явная история
восстанавливается детерминированно. Сохранять упорядоченные команды, chosen index,
old logp/value, публичные наблюдения, прошлые команды, outcome, episode boundaries.
При лимите RAM разрешён spill на диск без потери эпизодов. Тайминг порядка прихода
worker не должен определять seeds эпизодов или их inclusion: назначать episode ID
в фиксированном порядке и фиксировать wave-план сбора.

Ресурсные ориентиры: peak VRAM ≤14 GiB, RAM процесса и workers вместе ≤24 GiB.
Это цели профилирования. При превышении сначала уменьшить spatial/time
microbatch и включить activation checkpointing; не урезать действия, память
или minibatch без новой конфигурации. Предельное число env можно уменьшить
32→16 с записью изменения, сохраняя PPO batch и распределение сценариев.

Benchmark: 10 updates после 2 прогревочных, три повторения одинакового состава
нагрузки. Отдельно измерить simulation, greedy, encoding, inference, prefix
recompute, backward/optimizer, validation. Главная скорость — реальные решения
learner в секунду полного цикла. Числа из `artifacts/combat/benchmark.json`
измеряют другое и не прогнозируют скорость обучения.

Прогноз длительности: `budget / measured_decisions_per_second` плюс измеренное
время evaluation/checkpoint. Например, 2 млн при 500 решениях/с — 1.11 часа
только основного цикла; при 100/с — 5.56 часа. Это арифметика, не обещание.
30 млн на три seed полного одного варианта, 90 млн для A/B/C, без повторов
поиска гиперпараметров. Полный бюджет предлагается после pilot и замеров.

## 13. Checkpoint, журналы и возобновление

Во время обучения, оценки и benchmark отдельный sampler раз в секунду пишет
`resources.jsonl`: UTC/elapsed time, фазу, update, решения; CPU всей системы и
дерева процессов (100% процесса = одно логическое ядро), суммарный RSS дерева,
системную RAM; занятую/полную VRAM, GPU Core Load, GPU Memory Controller Load,
полную мощность платы в ваттах и процентах штатного power limit NVML.
Сохраняются штатный и enforced power limits; штатный лимит — явно обозначенный
знаменатель/приближение TDP, а не произвольно заданные 100%. GPU-счётчики берутся
через NVIDIA NVML, **не WDDM D3D Usage**. Memory Controller Load обозначает долю
времени чтения/записи памяти, а не занятую ёмкость или процент пиковой полосы.
Это показатели всей платы, включая другие приложения. Недоступное поле — null
с причиной, без подмены на ноль. Схема и агрегаты лежат рядом; telemetry не
меняет RNG и не входит в детерминированный результат игры.

Каталог `artifacts/rl/<run_id>`: resolved config, spec/schema versions,
git commit и dirty diff, хеши ядра/AI/opponents, rules passport, корпус manifest,
environment lock, metrics.jsonl, checkpoints, evaluation, selected_replays.

На границе каждого update атомарно сохранять model, optimizer, расписания,
счётчики, RNG всех генераторов, sampler state/next episode IDs, версии corpus
и opponents, best-validation checkpoint metadata. Все среды к этой границе
завершены, hidden reset. Если прерван сбор/update, откатить к последнему
завершённому update и повторить его данные; не продолжать с частично обновлённым
optimizer. Зафиксированный wave-план позволяет повторить порядок эпизодов.
Файлы сохранять через временный файл и атомарную замену на том же диске.

Хранить последние 3 checkpoints, лучший validation и milestones 0.25/1/2/5/10
млн; совпадающие checkpoints не дублировать. Evaluation scores и manifest
не удалять при ротации. Все тестовые реплеи сохранять и верифицировать штатным
ядром; тренировочные — по 1 на каждые 1000 эпизодов и все ошибки.
Сохранение выборочных реплеев не меняет training RNG.

На каждый update: число решений/эпизодов, W/D/L по сопернику/стадии/стороне,
размер overflow, длины эпизодов, returns/value/advantage statistics, policy/value
loss, entropy raw/normalized, KL, clip fraction, explained variance (N/A при
нулевой дисперсии returns), нормы градиентов, LR, скорость по компонентам,
VRAM/RAM. Невалидные/NaN поля не превращать в нули.

## 14. Обязательные проверки реализации

1. **Нет подглядывания.** Пары историй с одинаковой доступной информацией и
   различным скрытым миром дают одинаковые признаки, команды, logits и value.
   Проверять видимость, потери, движения, список команд, metadata и labels.
2. **Геометрия.** Обе row_parity, шесть направлений, обратные рёбра рек,
   boundary_rivers, правильное расстояние; padding не соседствует с картой.
3. **Память.** Возраст растёт от ходов противника, не от собственных команд;
   повторный контакт обновляет ID; исчезновение не читает скрытую смерть;
   reset и независимые стороны не смешивают историю.
4. **Среда.** Один и тот же поток команд даёт тот же исход, что run_match;
   поражение на ходе соперника, ранняя победа, обе стороны, лимит, terminal reward.
5. **PPO.** При неизменных весах ratio≈1; terminal returns имеют нужный знак;
   padding/префиксы не участвуют в loss; аналитические игрушечные эпизоды
   подтверждают loss/градиент и gradient accumulation с неполными chunks.
6. **Recurrent replay.** Полный прогон и prefix+chunk дают одинаковые logits/h
   при фиксированных весах; после смены весов префикс действительно пересчитывается.
7. **Продолжение.** На контрольном CPU FP32 прогоне прерванный и непрерывный
   запуск совпадают; GPU сравнивается в рамках возможностей выбранного backend.
8. **Корпус.** Нет пересечений parent worlds/hashes между splits, все карты
   проходят ограничения, каждый тестовый сценарий и side-pair воспроизводим.
9. **Исполнение.** Экспортированный агент выполняет штатный матч; сохранённый
   реплей проверяется ядром; standalone и batched inference совпадают в допуске.

Короткое переобучение одного фиксированного боя допустимо как технический тест
обучаемости, но не включается в доказательство переноса или полезности памяти.

## 15. Приёмка и порядок экспериментов

### 15.1. Техническая приёмка

Проверки раздела 14 проходят; 32 768-step smoke завершается с конечными loss
и градиентами, checkpoint восстанавливается, новые матчи и реплеи работают.
Ни одного скрытого входа или незаконной команды. Зафиксированы замеры скорости
и оценка бюджета. Высокий win rate для технической приёмки не требуется.

### 15.2. Pilot

Один C, seed 17, до 2 млн решений. Оценивать только на validation и dev-сценариях
памяти; финальные test-наборы не открывать. Сравнить с начальной случайной сетью
и fixed opponents; предоставить кривые и 6–10 полных боёв из разрешённых наборов,
включая поражения и ничьи. Если сигнал не возникает, сначала проверить данные и обучение,
затем менять по одному компоненту. Не масштабировать неработающий pilot.

### 15.3. Подтверждение результата

После работающего pilot — A/B/C по три seed, одинаковый бюджет до 10 млн
решений на seed. Seed 17 варианта C можно продолжить с 2 млн, только если
спецификация и расписание не изменились; иные варианты начинаются с нуля.

Предложенные инженерные пороги, не обещание достижимости:

- На основном test: средний score против greedy ≥0.60, нижняя граница 95%
  интервала >0.50; каждый training seed отдельно имеет point score >0.50.
- Против random средний score ≥0.90; W/D/L показываются, ничьи не скрываются.
- На диагностике памяти: B либо C лучше A минимум на 0.05 score, нижняя
  граница парного 95% интервала разности >0. Критерий сравнения заранее
  выбрать по validation и зафиксировать до открытия test.
- Добавочную пользу GRU заявлять только при положительной подтверждённой
  разности C−B. Если B не хуже C, сохранить B как практическую модель и
  признать, что ценность GRU в этом масштабе не доказана.
- Предметная проверка: пользователь получает полные бои с обзором игрока,
  историей контактов и переключением полной картины, включая случаи плохой игры.

Порог 60% — рабочая цель этапа; убедительность зависит также от состава
корпуса, устойчивости по мирам, seeds и качества поведения. Преимущество
только на специально сконструированной диагностике не заменяет общие бои.

### 15.4. Ограниченный порядок изменений

Сначала ошибки и производительность, затем curriculum/сигнал, затем память,
после — размер модели. Следующие разрешённые отдельные пробы:

| Наблюдение | Проба | Что фиксировать |
|---|---|---|
| Ранние KL-stop почти каждый update | LR 1e-4 вместо 3e-4 на старте | Остальные PPO параметры |
| Энтропия рушится до освоения боя | Начальный entropy 0.02 | Curriculum и budget |
| Дальняя история не используется | BPTT 256 вместо 128 | Minibatch решений, число seeds |
| Точный prefix слишком дорог | Burn-in 64 со старым h | Ошибка h/logits, качество, wall time |
| Слабое представление скрытого врага | D: belief_coef=0.1 | Те же входы actor |
| Локальный радиус ограничивает манёвры | 6 hex-блоков вместо 4 | Budget и размер/скорость |

При BPTT=256 использовать 4 chunks на minibatch, сохранив максимум 1024
позиций. Изменение gamma, награды, terminal rules, списка команд или использования
привилегий — новая версия постановки, не очередная настройка того же опыта.

Self-play — следующий этап после базового результата: смесь frozen snapshots
и алгоритмических соперников, с отдельным протоколом. В RL-01 не требуется
реализовывать лигу, Elo, MCTS или копирование действий CP.

## 16. Обоснование и источники

Приведённые работы поддерживают выбор семейства методов, но не задают наши
размеры, коэффициенты, curriculum и пороги: последние являются проектными
решениями, проверяемыми экспериментально.

- [PPO, Schulman et al.](https://arxiv.org/abs/1707.06347): clipped policy
  objective и повторные обновления на свежем наборе траекторий.
- [Recurrent Model-Free RL, Ni et al.](https://proceedings.mlr.press/v162/ni22a.html):
  рекуррентная модель как содержательная база для частичной наблюдаемости.
- [Invalid Action Masking, Huang & Ontañón](https://arxiv.org/abs/2006.14171):
  обоснование выбора только из допустимых действий. Отсутствие утечек через
  список действий при тумане — отдельное требование нашего симулятора.
- [PyTorch GRU](https://docs.pytorch.org/docs/2.15/generated/torch.nn.GRU.html):
  контракт recurrent state и размеров реализации.
- Локальные контракты: [боевое ядро](combat.md), [Combat AI](combat-ai-contract.md),
  `civ5sim/engine.py`, `civ5sim/match.py`, `civ5sim/agents.py`.

## 17. Производительный сбор v1.5

Рабочие артефакты находятся в `artifacts/rl/corpus`, `training-result` и
`performance-results`. Промежуточные версии и исходные метаданные до
переноса сохранены в `artifacts/rl/development-history.zip`. Корпусные пути
в текущем manifest относительны корню проекта. `training-result/relocation.json`
фиксирует замену путей/паспортов и проверку неизменности model, Adam, RNG и
счётчиков checkpoint; история результатов и все 204 updates сохраняются.

Отдельная конфигурация `configs/rl-v1-throughput.json`: 128 сред, четыре CPU
workers по 32 среды, `collection_scheduler=ready`. Minibatch PPO остаётся
8 chunks; веса заморожены на весь rollout, начатая волна полностью завершается
перед обновлением. Между обновлениями эпизоды и память не переносятся.

Worker кодирует только player observation и legal actions, ведёт свой encoder
и previous action для каждого боя. Семь массивов Encoded передаются через
фиксированные shared-memory slots. Parent копирует их до отправки следующей
команды, сохраняет вместе с raw observation и использует для PPO без повторного
кодирования. Проверяются variant и число решений. Списки команд больше shared
capacity передаются целиком через Pipe; обрезания legal actions нет.

Parent принимает уже готовые workers, объединяет доступные ответы в inference
batch и немедленно возвращает команды. Остальные workers в это время продолжают
симуляцию, противника и кодирование. Завершённые слоты не переиспользуются до
конца волны. Порядок хранения эпизодов остаётся исходным. Размеры inference
batch зависят от времени готовности процессов: побитовая повторяемость будущих
траекторий после resume не заявляется. Состояния модели, Adam, счётчиков и всех
RNG в checkpoint сохраняются полностью; граница pause/resume — завершённый update.

Greedy повторно использует геометрию публичной карты для legality probes.
Перед каждой пробой ВСЁ динамическое состояние восстанавливается из текущих
видимых units; данные исчезнувших контактов в следующую пробу не переносятся.
Боевые правила и критерии выбора команды остаются прежними.

Смена 32→128 сред меняет группировку завершённых партий по updates. Продолжение
пилота фиксируется как `rl01.pipeline_migration` в новом каталоге с parent SHA256,
перечнем изменений и исходной отметкой decisions. Проверка разрешает только
перечисленные настройки сборщика и исходники реализации; модель, награда,
PPO/Adam, точность, curriculum, корпус и native kernel должны совпадать.
Стандартный resume по-прежнему требует точного совпадения паспорта.

Для BF16 spatial encoder использует одинаковые блоки по 32 наблюдения при
выборе команды, проверке replay и обучении. Последний неполный блок дополняется
независимыми строками, которые отбрасываются до GRU и loss. Это устраняет
зависимость BF16 GEMM округления от большого различия row count между шаговым
inference и PPO; параметры и формулы сети не меняются. Пропускная способность
измеряется с учётом дополнительных вызовов и padding. Проверка полного
распределения behavior/replay сохраняет прежние пороги; old_logp не заменяется.

Производительность проверяется на замороженных train сценариях и полным циклом:
три повтора, два warmup и десять измеряемых updates, размеры карт 10/12/16.
Отчёт включает decisions/s, collection/cache/PPO wall time, полное распределение
behavior/replay, CPU/RAM/VRAM и NVML Core/Memory Controller/Power % default TDP.
Финальные test и diagnostic_test при этих проверках не открываются.
