# Следующий этап: PPO от имитации, против обычного CP

2026-11-05. Направление и основные параметры; реализация/обучение не запускались.

## Цель и старт

Научить политику выбирать команды ради победы в полном бою. Старт —
cp-imitation-own-states/cycle-02/checkpoints/step-0500.pt: 18/64 argmax
побед над CP, 2/64 sample. Начальная архитектура C/GRU и публичные признаки
сохраняются. Это один опыт, seed 17, без третьего цикла BC и без новых микрозадач.

С этого опыта argmax — основной режим оценки игровой силы; sampling T=1
нужен для on-policy обучения и остаётся отдельной контрольной оценкой.
Предыдущий sampling-критерий не переписывается. Цель проекта 75% побед
сохраняется, но не обещается за этот ограниченный бюджет и не объявляется
достигнутой по одному validation seed.

## Игры

- Прежние 57 training-worlds / 228 crops, новые расстановки и streams.
  10×10, воин+лучник по 100 HP, 30 раундов, fog/random damage.
- Обе стороны и контактные/разделённые старты сбалансированы.
  Противник в обучении — 100% обычный CP с прежним SearchConfig и
  привилегиями. Greedy остаётся контрольным соперником оценки.
- Сеть получает только собственные публичные наблюдения. CP сохраняет
  очередь и группы по штатным правилам, без discard_tactics.
- Подключить полный контракт CP к DecisionEnv: act_with_planning,
  временные planning services и on_action_result после реально исполненной
  команды, включая терминальную. Сейчас DecisionEnv вызывает обычный act;
  подстановка имени cp в конфиг сама по себе недостаточна.
- CP-советчика на стороне сети нет; новые supervised labels не собираются.
  Начальное умение действует через веса политики.

## Награда и critic

Только terminal reward: победа 1, поражение 0, ничья 0; промежуточная 0.
Лимит раундов — терминальная ничья, не bootstrap truncation. Gamma=1,
lambda=1, полные эпизоды, Monte Carlo return. Без бонусов урона,
разведки, штрафов за команды и повторение. Техническая ошибка прерывает
update с сохранением воспроизведения, не становится игровым поражением.

Это намеренный выбор цели P(win). При +1/0/−1 агент оптимизировал бы также
замену поражений ничьими. Цена выбранной цели: начальная информация
о полезных действиях поступает от редких побед; частоту побед показывать
на каждом rollout, не скрывать за средним reward.

Actor и общий encoder/GRU загрузить из BC. Value head разморозить,
её последний линейный слой (weight и bias) обнулить: начальный V=0.
Прочие веса не переинициализировать. Adam создать заново для PPO,
моменты BC не переносить. Отдельной кампании прогрева critic не проводить.
Проверить, что изменение critic не меняет исходные policy logits/GRU.

## Бюджет и обновления

| Параметр | Значение |
|---|---|
| Новые реальные решения learner | 1 048 576, закончить начатую волну |
| Размер rollout | минимум 8192 решений, только полные эпизоды |
| Среды / CPU workers | 128 / 4, по 32 среды |
| Политика при сборе | sampling T=1, заморожена на весь rollout |
| PPO epochs | максимум 4 на rollout |
| Решений на шаг Adam | 1024 непустых временных позиции, последний остаток фактический |
| Microbatch / фрагмент | 8 последовательностей / 128 позиций |
| LR | постоянный 1e−4 |
| Adam | betas 0,9/0,999; eps 1e−5; weight decay 0 |
| PPO clip | 0,2 |
| Value coefficient | 0,5; MSE без множителя 1/2, без value clipping |
| Entropy coefficient | 0, без дополнительного поощрения случайности |
| Gradient clipping | global norm 0,5 |
| KL stop | 0,015 после каждого Adam step, по всему rollout |

LR/entropy schedules отсутствуют. Все счётчики PPO начинаются с нуля;
ни Adam counter 2480, ни BC-предъявления не расходуют бюджет решений.
Решения включают forced steps, чтобы сохранить текущую PPO-семантику
и историю; свободные решения дополнительно считать и публиковать.
KL основного stop считать по свободным решениям (>=2 легальных команд),
чтобы forced states не разбавляли изменение политики. Шаг, пересёкший
порог, сохранить и остановить дальнейшие шаги этого rollout, как в D1.
Не использовать rollout повторно в следующем update.

Advantage = terminal return − сохранённый old_value, нормализация по
реальным временным позициям rollout как в действующей реализации.
Forced steps имеют нулевой actor-gradient и участвуют в critic/history.
Маски padding обязательны. Current-weight GRU prefixes без градиента;
сброс памяти между эпизодами. Numerics остаются прежними: BF16 spatial,
FP32 GRU/heads/loss, spatial block 32. Оптимизации own-states переносить
только в пределах подтверждённой эквивалентности PPO forward/backward.

Верхняя граница — 2 часа активного wall time сбора и PPO-обновлений
суммарно. Включать runtime compilation внутри update; отдельно учитывать
первичную подготовку, оценки и паузы. Остановиться по первому пределу,
сохранить фактические решения/эпизоды/Adam steps и причину. Не продлевать
автоматически. Это ограниченный бюджет, не обещание скорости.

Первые три штатных rollout дают ETA и входят в опыт. Если заявленный
объём не помещается, продолжать в пределах двух часов с честным недобором,
а не превращать это в отдельный performance-проект. GPU NVML записывать;
для длительной GPU-фазы действует AGENTS.md. Исключение пользователя для
own-states автоматически на этот опыт не переносится. Ни CPU-сбор,
ни оценки не включать в среднюю загрузку GPU-фазы.

## Оценка и выбор

На нуле и после пересечения 131072, 262144, 524288 и 1048576 решений:
прежние 64 validation-матча против CP и 64 против greedy в обоих режимах.
При остановке по времени добавить оценку последнего checkpoint, если
он ещё не оценён. Baseline запускать заново только при отсутствии
доступных сохранённых per-match результатов или изменении evaluator.

Выбор кандидата: максимум argmax wins против CP на этой development-оценке,
tie — более ранняя модель; исходная BC входит в кандидаты. Ничьи, CE,
greedy и sampling не меняют правило выбора. Показать learning curve,
а не только лучший checkpoint. Развести номера PPO updates и Adam steps.

Для итоговой проверки до обучения зафиксировать дополнительный manifest:
на каждом из 16 validation-worlds восемь новых расстановок (четыре
контактные, четыре разделённые), каждая с обменом сторон — 256 матчей.
Не использовать их в выборе checkpoint. После выбора один раз оценить
baseline и кандидата argmax против CP: 512 матчей суммарно. Test закрыт.
Это дополнительная проверка расстановок внутри знакомых validation-миров,
а не независимый test новых миров. При совпадении весов результат переиспользовать.

Основной измеримый результат этапа — рост argmax win rate над BC на этих
256 матчах с положительной нижней границей 95% парного bootstrap CI
по 16 parent-worlds. Практический ориентир — прирост хотя бы 10 п.п.;
меньший подтверждённый прирост полезен, но требует оценки темпа прогресса.
Ничьи победами не считаются. Даже 75% на этом наборе потребуют отдельного
подтверждения, прежде чем объявлять общую цель выполненной.

## Проверки и решение после опыта

До продолжительного сбора: короткое сравнение DecisionEnv и обычного
match runner на одинаковых сценариях/seeds и записанных командах learner,
сверка CP-команд, outcomes и state hashes. Проверить память между
эпизодами, terminal reward и неизменность policy при сбросе value output.
Существующие pre-update replay/logp checks PPO обязательны. Полный suite
и общий рефакторинг runner не входят в этап.

Каждый update публикует training W/D/L, долю побед, free/forced counts,
entropy, KL, выполненные Adam steps и critic mean/MSE/explained variance.
Если побеждающих эпизодов нет, явно показать отсутствие положительного
сигнала; это не основание молча добавить shaping или изменить reward.

При устойчивом росте — масштабировать бюджет/подтверждать другим seed.
При росте train wins без validation — работать с обобщением и покрытием.
При отсутствии роста train wins — разбирать положительный сигнал,
critic и движение политики по KL, а не запускать ещё один BC-цикл
по умолчанию. Изменение награды/температуры/архитектуры будет отдельным
решением после этого опыта. Большие армии 16×16 пока не включать:
это изменит задачу одновременно с переходом от имитации к RL.
