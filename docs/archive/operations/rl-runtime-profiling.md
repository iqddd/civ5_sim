# Профилирование Collection на разных CPU

> Архив: исторический протокол, исследование или прежний справочник.
> Числа, команды, версии и формулировки «следующий шаг» относятся к описанному этапу.
> Проверенные статусы и ограничения: [журнал](../../experiment-ledger.md); текущее устройство: [справочник](../../rl-architecture.md).

Измеряем фиксированную работу на замороженной политике. Обучение, optimizer,
shuffle RNG и счётчики опыта не изменяются. Меньшая загрузка GPU сама по себе
не является регрессией: основной критерий — время одинакового Collection.

## Воспроизводимый вход

Нужны сохранённый rollout с публичными историями, checkpoint и конфигурация.
Используем один и тот же набор полных эпизодов, seed, CP и веса модели для
всех кандидатов. Последняя волна может содержать меньше эпизодов: Collector
завершает каждый из них полностью. Кратность числу сред или workers не нужна.
Нельзя менять карты, армии, горизонт, поисковые бюджеты CP или reward ради
скорости. Не переносим выбранное число workers между процессорами автоматически.

Команды ниже выполняются из корня проекта через Python окружения опыта.
На Windows здесь используется `.venv\Scripts\python.exe`; на Linux — Python
подготовленного окружения.

## 1. Последовательный CPU replay

```powershell
.venv\Scripts\python.exe tools/profile_rl_runtime.py cpu --rollout artifacts/rl/ppo-after-target-bc/rollouts/latest.pt --episodes 8 --repeat 3 --python-profile --out artifacts/profiling/cpu
```

Один прогрев не входит в медиану. Время включает reset, действия CP, симуляцию
и проверку сохранённых историй. Проверяются точное совпадение публичных
наблюдений, легальных действий, всех команд и результатов. `python.prof`
собирается отдельным дополнительным проходом, вне timed trials.

Для сравнения с прежней реализацией допустим `--source-root` на отдельный
checkout той версии с собранными native-библиотеками и теми же generated rules.
Не переключать исходники и DLL внутри работающего процесса.

## 2. Нативный профиль

```powershell
.venv\Scripts\python.exe tools/build_combat_ai.py --profile --dll-only
.venv\Scripts\python.exe tools/profile_rl_runtime.py cpu --rollout artifacts/rl/ppo-after-target-bc/rollouts/latest.pt --episodes 8 --repeat 1 --warmup 0 --native-library build/combat_ai_profile.dll --out artifacts/profiling/native
```

На Linux библиотека называется `build/libcombat_ai_profile.so`.
Диагностическая библиотека отдельная; production DLL не содержит таймеров.
Счётчики включают geometry build, root import, state export, tactical view,
board refresh, ABI validation и три вида запросов. Времена **inclusive**:
вложенные категории нельзя складывать. Сравниваем число фактически выполненных
операций и доли затрат; итоговое ускорение измеряем обычной библиотекой.

## 3. Полный Collection на CUDA

```powershell
.venv\Scripts\python.exe tools/profile_rl_runtime.py collection --config configs/rl-ppo-after-target-bc.json --checkpoint artifacts/rl/ppo-after-target-bc/checkpoints/update-0006.pt --rollout artifacts/rl/ppo-after-target-bc/rollouts/latest.pt --episodes 32 --workers 8 --reply-size 2 --repeat 3 --out artifacts/profiling/w8-r2
```

Число сред задаётся через `--envs`; без этого флага используется config.
В обычном обучении это верхняя граница ёмкости. Перед волной Collector оценивает
нужное число эпизодов как `ceil(оставшиеся решения / средняя длина эпизода)`
и ограничивает его ёмкостью. Начальная длина берётся из `episode_length_hint`,
предыдущего сбора тем же Collector или значения 128; после первой волны —
из завершённых эпизодов текущего сбора. Цель учитывает остаток `max_decisions`.
Все начатые эпизоды включаются целиком. В метриках сохраняются `wave_sizes`,
`target_decisions`, `rollout_decisions` и `rollout_overshoot`.
Например, `--envs 12 --workers 12 --reply-size 1` соберёт 32 эпизода волнами
12 + 12 + 8. Ёмкость может распределяться между workers неравномерно;
`reply-size` должен помещаться в максимальное число сред worker.
Эти runtime-параметры не переписывают config и случаи.

На каждом новом CPU сначала фиксируем модель CPU, физические ядра, логические
потоки/SMT, доступную RAM, GPU, версии Python/Torch, commit и SHA256 DLL.
Также сохраняются CPU affinity, cpuset, Linux cgroup v1/v2 CPU quota и доступная
память с учётом видимых родительских групп, если доступны:
в контейнере число ядер хоста может превышать выделенную CPU-квоту.
Команда сохраняет эти данные в `result.json`. Не предполагаем, что 12 потоков
равноценны 12 физическим ядрам или что число workers должно равняться одному
из этих чисел.

Кандидаты запускать **последовательно**, без параллельной компиляции, тестов или
других benchmark. Прогрев исключён из медианы. Для рабочего подбора ниже
достаточно первичного замера и одного повтора двух финалистов в обратном
порядке; это практический выбор, не точная оценка выигрыша реализации.
Фоновая нагрузка и холодная компиляция видны в телеметрии.

В `result.json` сравниваем:

- время собственно `collection_seconds` и решения/с;
- inference seconds, количество вызовов и средний batch;
- worker request/wait seconds, publish delay и idle slot seconds;
- точное совпадение command hash; небольшие различия FP32 log-probabilities
  от разных форм inference-batch записаны отдельно, как и recurrent/value;
- `compilation_seconds`, отдельно от установленной производительности.

`idle_slot_seconds` и worker request seconds суммируются по слотам/workers и
могут превышать wall time; это не дополнительные секунды длительности фазы.
Проверочные хеши вычисляются вне показателя `collection_seconds`.

NVML-телеметрия по фазам находится в `resources.jsonl`. Считать GPU Core Load
по непрерывным участкам нужной фазы, исключив warmup и compilation. Не подменять
его WDDM D3D Usage. Правило 80%/60 секунд из AGENTS.md относится к длительным
итеративным GPU-фазам; CPU-bound Collection не следует искусственно удлинять
или загружать бесполезной GPU-работой.

## Выбор и подключение

Выбираем вариант по времени одинакового Collection, сохранив корректность и
фиксированный состав эпизодов. Параметры исполнения передаются в Collector
через `num_envs`/`cpu_workers`/`reply_size`; config, checkpoint и manifest не переписываются.
Для нового runner настройки машины хранятся в отдельном runtime config и
фиксируются в артефактах при следующем явном запуске.

Текущий файл — `configs/rl-ppo-after-target-bc-runtime.json` с ключами
`cpu_workers` и `worker_reply_size`; необязательный `num_envs` задаёт ёмкость волны.
Другой файл передаётся runner через
`--runtime-config <path>`. Это не команда возобновления: запуск обучения
выполняется отдельно по явному решению пользователя.

## Короткий подбор на Linux и Windows

Из корня проекта, с уже собранными native-библиотеками и рабочим CUDA-окружением:
Используется **streaming** независимо от прежнего scheduler в конфигурации.
Общие правила сбора, точность, модель, CP и данные остаются прежними.

```bash
python tools/tune_rl_collection.py \
  --config configs/rl-ppo-after-target-bc.json \
  --checkpoint artifacts/rl/ppo-after-target-bc/checkpoints/update-0006.pt \
  --rollout artifacts/rl/ppo-after-target-bc/rollouts/latest.pt \
  --out artifacts/profiling/collection-tune --dry-run
```

Убрать `--dry-run`, чтобы выполнить подбор. Вместо отдельной исследовательской
кампании используется ограниченная процедура `streaming-quick-v1`:

1. `C` — минимум affinity/cpuset и CPU quota, с сохранением дробной квоты;
   `B = max(1, ceil(C))`. Например, 7,68 → 8 workers, 23,04 → 24.
   `--cpu-budget` переопределяет оценку для кандидатов, не меняет квоту ОС.
2. Начальная ёмкость `E = max(80, 2B)`, ограниченная числом доступных случаев.
   80 — практическая стартовая эвристика для нынешних боёв, не аппаратная
   константа и не найденный универсальный оптимум. По умолчанию берутся первые
   `2 * max(80, 2B)` случаев, ограниченные имеющимися, без повторения.
   `--episodes N` задаёт их число явно. Все варианты выполняют один набор.
   При коротком входе пополнения слотов может не быть; это видно в dry-run.
3. Три первичных варианта: `E/B/1`, `E/2B/1`, `E/E/1`. Workers ограничиваются
   ёмкостью, дубликаты пропускаются. Это позволяет увидеть и режим около
   CPU-квоты, и полезное превышение числа CPU, не связывая envs с workers.
4. Одна проверка ёмкости у лучшего варианта: половина envs, но не меньше workers.
   Если победила одна среда на worker — вместо уменьшения проверить две,
   не превышая числа случаев. Другие параметры остаются прежними.
5. Одна проверка `reply=2`, только если у текущего лучшего варианта не меньше
   двух сред на worker. Базовое значение — 1. Окна batching не подбираются:
   `inference_min_batch=0`, `inference_wait_seconds=0`.
6. Два финалиста получают по одному дополнительному замеру в обратном порядке
   относительно первичных запусков. Выбор по медиане обоих замеров. При разнице
   до 3% предпочесть меньше workers, затем envs и reply. Финалистом может стать
   менее затратный вариант в пределах 3%, даже если его первый замер не лучший.

Всего **не более пяти первичных вариантов и двух повторов**, общий предел
**600 секунд**, включая загрузку, прогрев и компиляцию. Расширение поиска,
поиск плато и автоматические дополнительные подтверждения не выполняются.
Для нового CPU запускается та же процедура, а не новый план экспериментов.

Для явного сравнения, без эвристического расширения:

```bash
python tools/tune_rl_collection.py \
  --config configs/rl-ppo-after-target-bc.json \
  --checkpoint artifacts/rl/ppo-after-target-bc/checkpoints/update-0006.pt \
  --rollout artifacts/rl/ppo-after-target-bc/rollouts/latest.pt \
  --episodes 32 --candidates 12/12/1,16/16/1 \
  --out artifacts/profiling/collection-12-vs-16
```

Каждый запуск изолирован в отдельном процессе: **по одному CP-вызову на каждом
worker**, затем короткий Collection-прогрев до восьми эпизодов и измерение
полного набора. Это исправляет асимметрию, когда прежний прогрев использовал
только первый worker. Короткий прогрев сначала покрывает размеры карт,
остальные случаи выбираются из разных частей набора; выбранные индексы и
длительность сохраняются отдельно. `--warmup-episodes N` меняет размер,
`--warmup-episodes 0` явно возвращает полный прогрев; `--warmup 0` у profiler
отключает прогрев. CPU replay сохраняет полный прогрев.
Короткий прогрев не гарантирует компиляцию всех форм batch: оставшаяся
`compilation_seconds` сохраняется внутри timed trial и не вычитается из времени.
Прогрев workers и Collection записывается отдельно; полный прогрев всех
случаев не требуется. Исторические результаты сохраняются со своим методом.
Trace и подписи прогрева не используются как эталон полного набора.
Для явно заданных `--candidates` выполняются только эти варианты и по одному
повтору финалистов. `--scheduler ready --candidates ...` оставлен для прямого
сравнения прежнего режима; автоматический поиск работает только со streaming.

`--budget-seconds` по умолчанию 600: включает загрузку, компиляцию и прогревы.
По границе времени активный profiler останавливается вместе с дочерними
процессами; очистка ресурсов может занять ещё несколько секунд. Частичные
результаты сохраняются, незавершённое подтверждение помечается `preliminary`.
Ошибки, OOM и несовпадение команд/исходов видны в отчёте; несопоставимый вариант
не участвует в выборе. Варианты с ошибками не заменяются автоматически упрощёнными.

Выход: `report.md`, `summary.json`, таблица в stdout, каталоги запусков с логами,
телеметрией и численными отклонениями от первого кандидата; готовый
`recommended-runtime.json` для `--runtime-config`. Существующие файлы настроек
и состояние обучения не меняются. При изменении числа сред могут сдвинуться
границы training rollout; это записывается как настройка следующего запуска,
а не маскируется под ускорение прежнего режима.

Основной показатель — **время полного Collection одинакового набора**, вместе
с ним решения/с и диапазон повторов. Объясняющие показатели — inference batch,
число вызовов, CPU, RAM, NVML; на Linux с видимой CPU-квотой автоматически
сохраняются дельты `cpu.stat`. Throttling, сумма ожиданий или низкая GPU load
сами по себе не исключают кандидата. Тяжёлая диагностика и ETW выключены.

Подбор выполняется один раз при смене машины или существенном изменении
нагрузки. Для обучения использовать готовый runtime-файл; следить за временем
Collection, решениями/с и фактическим размером/превышением rollout. Изменение
поведения модели может менять стоимость CP: ухудшение этих показателей не
означает автоматически регрессию диспетчера. Автоматический повтор подбора
внутри обучения и автоматическое возобновление не выполняются.

Перекрытие PPO с подготовкой карт или начальным CP-ходом — отдельная задача.
Перекрытие с полноценным сбором на старой политике, выбор первых завершившихся
эпизодов, меньший поиск CP и сокращённые бои меняют протокол. В эту процедуру
они не входят. Аренда Vast.ai выполняется последующим отдельным этапом.

## Сравнение машин: CP Serial, CP Parallel и Collection

`tools/benchmark_rl_machine.py` запускает три отдельных бенчмарка без обучения.
CP Serial выполняет фиксированные бои в одном процессе, CP Parallel подбирает
число CPU workers для тех же боёв. Collection использует существующий подборщик
env/workers/reply и замороженные веса. Общего среднего балла нет: для аренды
главный показатель — Collection, два CPU-балла объясняют его ограничения.

Комплект создаётся один раз. На всех машинах используется ровно указанное число
эпизодов, независимо от quota. Набор, порядок, seeds, CP, точность и веса фиксированы:

```bash
python tools/benchmark_rl_machine.py prepare \
  --config configs/rl-ppo-after-target-bc.json \
  --checkpoint artifacts/rl/collection-vast-live/inputs/checkpoint.pt \
  --rollout artifacts/rl/collection-vast-live/inputs/rollout.pt \
  --episodes 80 --name combat-cp-v1 \
  --collection-reference artifacts/rl/collection-vast-live/iteration-1/collection-tuning/summary.json \
  --out artifacts/benchmarks/combat-cp-v1
```

`--collection-reference` необязателен. Он фиксирует команды и исходы уже
подтверждённого Collection. В комплект копируются checkpoint целиком, rollout
и конфигурация с раскрытым наследованием. Optimizer не загружается в модель.
Если rollout длиннее выбранного числа, файл сохраняется целиком, но во всех
тестах используется только фиксированный префикс. Не удаляйте и не меняйте
комплект после начала сравнения машин.

`manifest.json` содержит хеши файлов, исполняемых исходников, измерительных
скриптов, характеристику покрытия и ID версии нагрузки. CRLF/LF исходников
нормализуются для переноса Windows/Linux; содержимое входных файлов проверяется
побайтно. Изменение CP, симулятора или методики требует нового комплекта.
Сборки C++ могут различаться между ОС: фактический SHA библиотеки сохраняется
в результатах profiler. Следует использовать одну версию Python/зависимостей
из `requirements-rl.txt` и обычную оптимизированную сборку CP, без profile-таймеров.

В `combat-cp-v1` — 80 боёв: карты 10/12/16 представлены 31/25/24 случаями,
есть все армии 5–13 и пять типов юнитов, стороны 43/37, старты contact/separated
38/42, длительности до 10 / до 20 / свыше 20 раундов — 24/28/28.
Это рабочий набор для текущего класса задач; он не обещает универсальный
рейтинг процессоров. CPU replay воспроизводит записанные действия learner,
Collection заново выбирает их через checkpoint. В данном комплекте это
8592/21407 learner decisions/общих команд для CPU и 8253/20435 для Collection:
запись получена до PPO update 6, а checkpoint — после него. Внутри каждого
бенчмарка работа фиксирована; времена двух разных бенчмарков не складываются.

Первый эталон получен на Vast machine 120084 (i9-14900KF, quota 15.36,
1×4090): CP Serial 47.464 с (47.448–47.556), CP Parallel 7.095 с
(7.095–7.167, 15 workers), Collection 10.574 с (10.475–10.662, 30/30/1).
Каждому присвоено 100 баллов. CPU Parallel быстрее Serial в 6.69 раза.
CPU-замеры заняли 400 с общего runner-бюджета; Collection переиспользован
из подтверждённого предыдущего подбора той же машины. Результат:
`artifacts/benchmarks/vast-120084/run/summary.json`.

На подготовленной Linux/CUDA-машине с собранными native-библиотеками:

```bash
python tools/benchmark_rl_machine.py run \
  --bundle artifacts/benchmarks/combat-cp-v1 \
  --out artifacts/benchmarks/machine-1 \
  --machine-label machine-1 --price-per-hour 0.4134444444
```

Для последующих машин добавить
`--reference artifacts/benchmarks/machine-1/summary.json`. Каждый балл равен
`100 * reference_seconds / machine_seconds`; первая машина получает 100.
При другой версии нагрузки сравнение запрещено. При несовпадении команд,
исходов или класса GPU Collection не получает сопоставимого балла.
Небольшие FP32-отклонения probabilities/hidden/value сохраняются отдельно.
Неподтверждённые результаты не получают окончательных баллов.

Общий бюджет по умолчанию — 900 секунд после запуска скрипта, включая проверки,
создание процессов, прогревы, компиляцию и подбор. На CPU-проверки отводится
не более 45% этого бюджета, остаток — Collection. Это ограничение времени
измерения, а не изменение нагрузки. По исчерпании сохраняются частичные
результаты со статусом `preliminary`; обучение и аренда автоматически не запускаются.

CP Serial: одна полная сверка публичных историй вне timed trials, полный прогрев
и три замера. CP Parallel: точки около B/2, B, 1.5B и адаптивное расширение,
как в Collection; лучшие две подтверждаются тремя измерениями с чередованием.
В пределах 3% предпочтение меньшему числу workers. Процессы `spawn` заранее
загружают компактные команды без Torch; внутри прохода эпизоды выдаются по
готовности workers. Измеряется общее wall time, включая выдачу работы и возврат
результатов; проверка команд, порядка и исходов выполняется после остановки таймера.
Проверку публичных историй повторно не выполняют для каждой настройки:
передаётся проверенный результат той же записи/сборки. Каждый эпизод получает
новый `DecisionEnv`; остаточные сообщения предыдущего прохода не используются.

И у CP Parallel, и у автоматического Collection ёмкость ограничена половиной
фиксированного набора (40 для этой версии). Выход на предел явно отмечается
`at_search_limit`; мощная машина может быть недооценена. Прогрев, загрузка и
компиляция показаны отдельно. Основной результат — медиана трёх подтверждений,
также сохраняются минимум/максимум и флаг `unstable` при разбросе свыше 10%.
NVML/CPU/RAM находятся в JSONL по фазам, GPU Core Load не используется как балл.

Для первой удерживаемой машины допустимо переиспользовать подтверждённый
Collection через `--reuse-collection path/to/original/summary.json`.
Принимается только точный файл, зафиксированный в комплекте; сверяются CPU,
quota, affinity, платформа и класс GPU. Этот флаг предназначен для исходной
машины и не проверяет её физическую идентичность по CPU-модели. При его
использовании весь оставшийся бюджет доступен CPU-тестам.

Выход: `summary.json`, `report.md`, логи и profiler-результаты каждого запуска,
`recommended-runtime.json`. Вместе с баллами сохраняются цена, баллы/($/час),
стоимость миллиона решений **только Collection**, отдельные счётчики CP и
Collection. Цена установки окружения, PPO и боевых оценок в эту стоимость
не входит. Для сведения нескольких машин в таблицу:

```bash
python tools/benchmark_rl_machine.py compare \
  artifacts/benchmarks/machine-1/summary.json \
  artifacts/benchmarks/machine-2/summary.json \
  --out artifacts/benchmarks/comparison
```

Первый указанный результат — эталон. Выход `comparison.json` и `comparison.md`.
Универсальный аппаратный рейтинг из этих баллов выводить нельзя: оценивается
доступная контейнеру машина под фиксированную работу с CP и конкретной GPU.

## Потоковый Collection v1

Новый режим включается явно через `collection_scheduler: "streaming"`.
Он допускает некратное workers число сред. Бои закреплены за CPU-процессами,
внутри процесса очередь переключается после каждой команды CP. Завершённые
слоты получают следующие эпизоды без ожидания всей волны. Один вызов
планировщика CP остаётся неделимым. Отдельный поток родителя принимает Pipe-
ответы во время отправки сценариев и ожидания GPU, предотвращая взаимную
блокировку больших сообщений в двух направлениях.

При создании CPU-workers лимиты `OMP_NUM_THREADS`, `MKL_NUM_THREADS` и
`OPENBLAS_NUM_THREADS` наследуются со значением 1 до импорта NumPy в spawned
процессе. После запуска workers исходное окружение родителя восстанавливается.
Настройка только внутри worker запаздывает: при большом числе процессов на
Windows OpenBLAS может завершиться с ошибкой выделения памяти ещё при импорте.

Пример подбора на Linux (обучение не запускается):

```bash
python tools/tune_rl_collection.py --scheduler streaming \
  --config configs/rl-ppo-after-target-bc.json \
  --checkpoint artifacts/rl/ppo-after-target-bc/checkpoints/update-0006.pt \
  --rollout artifacts/rl/ppo-after-target-bc/rollouts/latest.pt \
  --episodes 80 --budget-seconds 900 --out artifacts/profiling/streaming-v1
```

Сначала при ёмкости выбранного набора проверяются workers около B/2, B,
1,5B, 2B и числа случаев; B — целая часть доступного CPU-бюджета. Затем
проверяются ёмкости W/2W/4W, reply=2 и объединение inference до 8/16 позиций
с планируемым ожиданием 0,5/1 мс. Фактическая задержка зависит также от ОС
и измеряется отдельно. Базовый вариант отправляет batch сразу.
Дубликаты пропускаются; лучшие два варианта подтверждаются тремя чередующимися
измерениями. При разнице до 3% выбирается меньше workers, затем сред,
затем меньше ожидание и reply. Для streaming ограничение N/2 снято:
кандидаты обрабатывают одни и те же случаи с непрерывным пополнением.

Profiler поддерживает те же настройки отдельно:
`--scheduler streaming --inference-min-batch 8 --inference-wait-seconds 0.0005`.
Если все активные среды уже ожидают inference, batch отправляется сразу.

`recommended-runtime.json` содержит `num_envs`, `cpu_workers`,
`worker_reply_size`, `collection_scheduler`, `inference_min_batch`,
`inference_wait_seconds`. Runner принимает этот файл через существующий
`--runtime-config`. Текущие настройки и состояние приостановленного опыта
подборщик не заменяет.

В обучении ёмкость сред отделена от целевого объёма rollout. Число новых
эпизодов оценивается по оставшимся решениям и ожидаемой работе уже начатых
боёв. Оценка длины берётся из предыдущего rollout (без истории — 128 решений),
затем из завершённых эпизодов текущего сбора. При достижении цели или deadline
пополнение прекращается, все начатые бои завершаются. Их данные включаются
целиком, поэтому фактический объём и выход за бюджет могут превышать цель.
Границы rollout зависят от выбранного режима и записываются в метриках.

В streaming `worker_wait_seconds` — блокирующее ожидание очереди ответов,
`worker_receive_seconds` — время чтения/декодирования в приёмном потоке;
оно может перекрываться с другой работой. С прежним объединённым показателем
ready-режима напрямую их не сравнивать. Дополнительно сохраняются histogram
размеров batch, p95 задержки готовых наблюдений, число/максимальное время
CPU-порций, длительность завершения активных боёв после закрытия приёма,
целевой и фактический объём rollout. Главный критерий — полное время
одинакового Collection; высокая загрузка GPU сама по себе не является целью.

Изменение исходников меняет идентичность замороженного машинного бенчмарка.
Сравнение streaming хранится отдельным отчётом с прежними входными случаями;
исторические баллы и старый manifest не перезаписываются.

## Диагностика связи workers, очередей и batching

Для сопоставления ready 80/8/1 и streaming 80/8/1, 80/80/1 используйте:

```powershell
.\.venv\Scripts\python.exe .\tools\compare_ready_streaming.py `
  --out ("artifacts/benchmarks/ready-streaming-abc-" + (Get-Date -Format "yyyyMMdd-HHmmss"))
```

Порядок A/B/C/C/B/A, два измерения каждого варианта, общий предел 900 секунд
включает подготовку и завершение процессов. Приоритет всех процессов Above Normal,
batching 0/0; ETW и подробная диагностика выключены. Флаг profiler
`--warmup-workers` выполняет один CP-вызов в отдельной временной среде каждого
worker и проверяет подтверждение по PID. После него остаётся прежний короткий
прогрев на восьми случаях. Временные среды закрываются до Collection;
измеряемые случаи, seeds и бюджеты поиска не меняются.

Опциональный `--collection-diagnostics` в `profile_rl_runtime.py` включает
одинаковые измерения для всех streaming-кандидатов. В обычном обучении они
выключены; runtime-config и научный config не изменяются. Подробности сохраняются
в `diagnostics-NNN.json` каждого запуска: прогрев и полный Collection раздельны.
Схема 1, длительности и timestamps в ns. `perf_counter_ns` задаёт общую ось
процессов; `thread_time_ns` — CPU вызывающего потока. PID, native TID и пара
QPC/UTC с неопределённостью позволяют сопоставить выборку с ETW.

- `cp_decision` включает planning snapshot, CP-координатор и нативные запросы;
  `cp_callback` — обработку результата с новым observation. Оба вложены в
  `request_slice`; их суммы не прибавляются к нему. CPU-время процесса worker
  включает также остальные его потоки и работу вне этих участков. Его последний
  snapshot снимается в quiescent-точке после рабочей отправки, до финального
  diagnostic RPC; точная граница указана в `process_cpu_sampled_at_ns`.
  Финальное idle-ожидание до границы родителя сохраняется отдельно как wall,
  без выдуманной CPU-оценки частичного интервала. CPU приёмного потока есть
  в scope-метриках; process CPU родителя не дублируется в receiver-отчёте.
- `cpu_local_queue` — ожидание очередной кооперативной порции в worker,
  **не** ожидание runnable-потока в планировщике Windows. CPU/wall сохраняются
  также для slice, encoding и применения learner action. `worker_receive`
  включает блокирующее ожидание команды и decode; `worker_send` включает
  serialization и возможную блокировку Pipe.
- Метки observation-ready стоят до worker encoding. Далее отдельно измеряются
  encoding, ожидание публикации, publish→receive/decode, receive→accept родителем
  и accept→inference-prepare. Старый `completed_at` остаётся меткой после encoding.
- Подготовка batch/H2D, forward submit с выходными heads, блокирующее получение
  результата на CPU, выбор/запись действия, send и фактические receive/apply в
  worker разделены. `blocking_result_to_cpu` включает ожидание незавершённых
  GPU-операций, а не только копирование. CUDA events измеряют интервал stream
  forward+output; он может включать простои запуска. Дополнительного synchronize
  на каждый batch нет: используется существующее блокирующее получение результата.
- Gauges интегрируются по времени. Очередь полученных, но ещё не принятых
  родителем наблюдений измеряется в приёмном потоке. Worker сообщает локальную
  pending-очередь и занятость slice; родитель — ready/inference/active/idle и
  завершённые эпизоды. `worker_side_outstanding_slots` включает транспорт и
  ожидания worker и не является числом потоков, реально исполняющихся на CPU.
  После последнего admission отдельно интегрируется `tail_active_slots`.

Гистограммы имеют 8 bins на октаву, отдельный zero bin и overflow. p50/p95/p99
даны как приближённые верхние границы bin, обрезанные наблюдавшимся максимумом.
Count/sum/min/max точные для измеренных участков. CPU-clock может возвращать
ноль для короткого вызова; отношение CPU/wall отдельного такого вызова не
интерпретируется. Объём подробных событий ограничен reservoir-выборкой:
8192 у родителя и 128 на worker, с отдельным RNG. Промежуточных файлов на каждый
шаг нет; финальные счётчики workers запрашиваются после завершения Collection.
`diagnostic_export_seconds` и запись JSON не входят в `collection_seconds`.
Ресурсный монитор на время выгрузки переходит в `diagnostic_export`, чтобы
её CPU/RSS не попадали в показатели Collection.
Накладные расходы самих clocks/агрегации остаются внутри измерений; одинаковая
инструментация применяется ко всем кандидатам.

Подготовлен отдельный ограниченный сценарий, который **запускает измерения
только при явном вызове**:

```powershell
.venv/Scripts/python.exe tools/diagnose_rl_collection.py `
  --out artifacts/benchmarks/collector-diagnostics-12-80
```

Он использует прежние 200 случаев, замороженные checkpoint/config, 80 сред,
reply=1 и прогрев на индексах `0,2,6,25,50,75,100,125`. Порядок контролей:
12→80→80→12 без дополнительного ожидания. На 12 workers затем один раз
проверяются B1=8/5ms, B2=16/10ms, B3=16/20ms. Если ближайший соперник отличается
от лучшего менее чем на 3%, он повторяется один раз; при сохраняющейся близости
выбирается меньшее окно. Выбранный вариант подтверждается в порядке
лучший→80, затем 80→лучший. Перед парой резервируется время для обоих запусков.
Бюджет 900s включает spawn, прогрев, проверку и экспорт. Остаточная компиляция
входит в Collection, показывается отдельно и не вычитается.

Требуется точное совпадение 21145 решений, 53675 команд и результатов. Полные
trace-массивы сравниваются с `rtol=atol=1e-5`, как в существующих pipeline-проверках
FP32 roundoff; максимальные отклонения также сохраняются. Практический результат:
медиана свежих подтверждений 12 workers не более 103% от 80 при меньшей медиане
peak RSS дерева. Это не доказательство эквивалентности и не обещание ускорения.
При исчерпании бюджета незавершённое подтверждение явно отмечается.

После разбора отчёта можно отдельно собрать до 300s ETW, указав необъяснённый
эффект (CP wall/CPU, простой при pending-работе, очередь родителя или выигрыш 80):

```powershell
.venv/Scripts/python.exe tools/diagnose_rl_collection.py `
  --out artifacts/benchmarks/collector-diagnostics-etw `
  --trace-reason "Необъяснённый разрыв CP wall/CPU"
```

Это два прохода 12/80 без batching-ожидания, не участвующих в ранжировании.
Профиль WPR CPU содержит CSwitch, ReadyThread, SampledProfile и стеки.
Чужая WPR-сессия не останавливается. Без административных прав захват не
начинается; отсутствие символов может ограничить разбор нативных стеков.
ETW не запускается автоматически из основной серии. Ни один сценарий не
применяет runtime-настройки и не возобновляет обучение.

Результат локальной серии 2026-11-07: [разбор](../../../artifacts/benchmarks/collector-diagnostics-12-80-20261107/analysis.md).
Выполнено 10 запусков за 738.92s; вторая подтверждающая пара не запущена,
поскольку оставшиеся 161.08s меньше резерва полной пары 170.72s.
Одиночный B1 дал 52.326s против медианы исходных контролей 12/80 workers
53.687/51.969s. По правилу близости выбран B0; первая свежая пара
57.904/53.559s дала отставание 8.11%. Практический критерий не подтверждён,
runtime-настройки не применялись. Все команды/исходы совпали с эталоном.
ETW не запускалась из-за отсутствия административных прав; дополнительная

Серия 6/8 workers с приоритетом Above Normal, без контрольных повторов:

Каждый вариант измерен один раз после прогрева на прежних 8 случаях; дополнительные

Collector/Profiler теперь допускают неравномерное распределение ready-слотов,

Ограничения делимости отдельных training runner этим не меняются.

Для короткого парного ETW-захвата открыть **pwsh от администратора**:

```powershell
Set-Location E:\civ5_sim
.\.venv\Scripts\python.exe .\tools\diagnose_rl_collection.py `
  --out ("artifacts/benchmarks/windows-receiver-etw-" + (Get-Date -Format "yyyyMMdd-HHmmss")) `
  --budget-seconds 300 `
  --trace-reason "Receiver delays: 12 versus 80 workers; batched Windows waits"
```

Это только streaming 80/12/1, затем 80/80/1, с batching 0/0 и принудительным
Normal priority у parent и workers; по одному измеряемому проходу и короткому
прогреву на прежних случаях. Профиль WPR CPU пишет CSwitch, ReadyThread и
SampledProfile со стеками. Все стадии захвата ограничены общим deadline;
для сохранения ETL резервируется 30s. Времена этих проходов не ранжируются.
Каждый захват получает уникальный WPR `-instancename`; он используется также
для stop/cancel, включая неоднозначный timeout во время start. Аварийный cancel
и финализация отчёта входят в резерв общего бюджета; имена сессий сохраняются
до старта в `summary.json → trace_instances`.
`summary.json → captures` содержит отдельные границы Collection (UTC и ns),
QPC/UTC anchor и PID/TID parent, receiver и всех workers. Отфильтровать ETL
по этим границам: spawn, warmup и export в разбор Collection не включаются.
Исходники установленного `wait()` сохраняются в `python-wait-source.txt`;
порог >60 относится к фактически ожидающим handles, а не просто к числу
соединений. Сохранённые файлы — `scheduler-B0.etl` (12) и `scheduler-W80.etl` (80).
При неполной паре код завершения 2; подробность — в `report.md` и `summary.json`.
