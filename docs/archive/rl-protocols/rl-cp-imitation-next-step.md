# Следующий шаг: завершить первый опыт CP imitation

> Архив: исторический протокол, исследование или прежний справочник.
> Числа, команды, версии и формулировки «следующий шаг» относятся к описанному этапу.
> Проверенные статусы и ограничения: [журнал](../../experiment-ledger.md); текущее устройство: [справочник](../../rl-architecture.md).

2026-11-04. После проверки `artifacts/rl/cp-imitation`.
Смысл шага: получить первое сравнение **initial → BC в полноценных боях**.
Это продолжение уже реализованного опыта, не новая исследовательская ветка.

## Что запускаем

1. **Сбор:** добрать ≥20 000 training и ≥2457 holdout меток с альтернативами.
   Четыре CPU workers; восемь benchmark-эпизодов засчитываются. Один вызов
   `collect`, лимит 3600 с на оба split, завершать начатую волну. При недоборе
   остановиться и сообщить фактический объём, не перезапускать сбор автоматически.
2. **BC:** свежая C seed 17 из сохранённого initial, три эпохи, GPU/CUDA.
   Adam LR=1e−4, minibatch 1024 обучаемых метки, microbatch до 8 фрагментов,
   sequence length 128, clipping 0,5. CE без entropy/value loss. Лимит 1800 с
   optimizer work; preprocessing, compile и holdout измерять отдельно.
3. **Бои:** последний полностью завершённый epoch против CP и greedy;
   initial против тех же соперников; CP против greedy. По 64 матча на группу,
   всего **320**, неизменные validation cases/seeds. **CPU, 4 workers**, sample,
   temperature=1. Не выбирать лучшую эпоху по боевым результатам.

Оставить без изменений карты 10×10, армии воин+лучник по 100 HP, туман,
случайный урон, 30 раундов, SearchConfig CP, разбиение миров и все другие
параметры `configs/rl-cp-imitation.json`. Не увеличивать данные/эпохи по ходу,
не вводить class weights на основании шести melee-меток пилота. Value head
заморожена, но её численные предсказания могут меняться с общим encoder;
как обученный critic её результат не интерпретировать.

Не запускать PPO, seed 42, отдельные движение/GRU probes или закрытый test.

## Команды и условия перехода

Выполнять последовательно; не запускать следующую фазу, пока не проверен
итог предыдущей. Внутри этого единственного согласованного опыта дополнительных
остановок для обсуждения успешного завершения каждой фазы не требуется.

```powershell
.venv\Scripts\python.exe tools/run_cp_imitation.py collect --workers 4
# Продолжать только при collection.json: status == "complete".
.venv\Scripts\python.exe tools/run_cp_imitation.py train --device cuda
# Продолжать только при наличии last completed epoch / final_checkpoint.
.venv\Scripts\python.exe tools/run_cp_imitation.py evaluate --workers 4 --device cpu
.venv\Scripts\python.exe tools/run_cp_imitation.py report
```

Неполный training budget допускает оценку последней полной эпохи с явной
пометкой фактического бюджета. Если ни одной эпохи нет, не оценивать partial
как будто это final. При технической ошибке сохранить traceback/артефакты;
не менять источник данных или настройки, чтобы обойти паспорт запуска.

В evaluate сейчас **нет wall-time budget и нет штатного пропуска уже готовых
матчей**. Ограничение этого запуска — 320 игр с существующими round/command
guards, не обещание уложиться в 1,45 минуты. Плановый ориентир контроля времени
— 30 минут оценки: если за это время она не завершена, проверить прогресс и
стоимость уже выполненных матчей, а не автоматически убивать процесс или
повторно запускать все игры. Не выдавать неполную оценку за 64 матча на группу.
Добавлять scheduler/resume infrastructure только ради этого запуска не нужно.

Перед фазами достаточно существующей проверки source/config identity. Если
код после benchmark не менялся, не повторять full suite и дополнительные
benchmark. Две целевые проверки BC и полные реплеи benchmark уже проверены.

## Что обязательно показать в результате

Одна таблица: initial–CP, BC–CP, initial–greedy, BC–greedy, CP–greedy;
для каждой W/D/L и win rate, для BC — изменение относительно initial.
Показать отдельно contact/separated и обе стороны, чтобы агрегат не скрывал
провал одного режима. Ничьи не считать победами. Если давать интервал прироста,
парный bootstrap по 16 parent-worlds с сохранением обеих расстановок и сторон;
64 игры не считать 64 независимыми мирами.

Обучение: фактические метки/эпизоды/миры, частоты типов команд без forced,
initial и final holdout CE/accuracy по типам, динамика трёх эпох, реальные Adam
steps и общее время. Только усреднённый training loss эпохи недостаточен:
он измерен на меняющейся policy; сравнение holdout выполняется фиксированными
initial/final. Стоимость generation, training и evaluation разделить.

Посмотреть несколько полных боёв: победу, поражение, ничью, если они есть,
и характерное расхождение с учителем. Не строить новый набор диагностик.
Сохранить реплеи всех оценочных матчей, как уже делает runner.

## Какой следующий выбор позволит сделать этот запуск

- **Появились победы, BC заметно сильнее initial:** получили стартовую боевую
  policy. Только тогда обсуждать один опыт её улучшения, а не весь путь к 75%.
- **Holdout CE улучшилась, но боевой силы нет:** проверить собственные
  траектории сети — какие состояния и решения не покрыты demonstrations.
  Не объявлять недостаток архитектуры и не запускать PPO автоматически.
- **CE почти не сдвинулась:** различить ошибку обучения и недостаточный объём
  оптимизации. При 20 тысячах меток три эпохи дают примерно 60 Adam steps;
  это маленький бюджет, не доказательство предела BC.
- **CP сам слаб на этих validation боях:** результат учителя ограничивает
  интерпретацию BC. Отчёт должен показать это, не подменяя цель победами над greedy.

Конечная цель — 75% побед над CP на целевых обычных боях — сохраняется.
Этот запуск отвечает на ближайший вопрос: даёт ли имитация полезную исходную
силу, с которой есть смысл продолжать работу. Порог 75% в малой выборке этого
опыта не служит окончательным подтверждением конечной цели.
