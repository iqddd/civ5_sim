Актуальная версия указана в [контракте](combat-ai-contract.md). Источник:

Это замена первых двух механизмов из таблицы экспериментов в рабочем

Она не закрывает полную приёмку CP-07 и не обещает идентичного поведения

тактический слой. Остальные задачи координатора не переработаны.

`plot_score` и `potential` прежнего `Search` удалены. Предварительная оценка
занятого назначения не копирует ветку, не удаляет блокировщика, не меняет
позицию/HP и не расширяет обзор. Физическая ветка копируется после отбора
кандидатов. Исполнение каждой команды остаётся через адаптер ядра; при
расхождении гипотезы с реальным переходом непригодная ветка отбрасывается.

С 0.9.2 перенесён `CORE_DELAYED_VISIBILITY=1` из базового CP:
`CvPlot.h:611–617` возвращает накопленный максимум, `CvPlot.cpp:11424–11427`
обновляет его при изменении источников, `flipVisibility:11391` и
`CvPlayer.cpp:32838/32959` сбрасывают его при начале/окончании хода.
`FindBestUnitAssignments:10408` и `getPlotsWithChangedVisibility:9239`
читают накопленный обзор. Прежнее мгновенное сужение в симуляторе было
недостатком переноса игрового состояния, не эвристикой CP или координатора.
Ветви принимают накопленную маску из запроса, сохраняют её при клонировании
и расширяют при движении; реальная панель читает ту же маску из ядра.

В исходнике `GetSimulatedDamageFromAttackOnUnit` параметр с именем
`iExtraDefenderDamage` в ближнем бою передаётся в
`GetMaxAttackStrength(..., iAssumeExtraDamage)`, то есть ослабляет атакующего.
Для дальнего боя он ослабляет защитника. В 0.9.3 ошибка ближней ветви
исправлена в симуляторе: дополнительные ранения ослабляют защитника в обоих
режимах. Независимая проверка сравнивает силы с физически раненым защитником.
Игровой исходник и DLL пока не исправлены; заметка лежит рядом с исходником.
Сохранён фактический
массив `hpLimit[5] = {70,40,20,-5}` с исходной индексацией: LOW/MEDIUM/HIGH/
BRAVEHEART используют 40/20/−5/0. Сравнение `remaining==maxMoves`, переданное
исходником как `bHasMoved`, также не переименовано по предполагаемому смыслу.
Проверка границы массива при сохранении равных оценок выполняется до чтения.

## Граница игровых запросов

Действующие границы запросов, две модели угроз и отсутствующие входы описаны
в [контракте](combat-ai-contract.md#физическая-модель-информация-и-память),
[оценки и допуск](combat-ai-contract.md#область-допуск-и-оценки) — там же.
Это заменяет прежний отдельный нормативный блок этого документа.

При переносе использованы запросы симулятора для поддерживаемых сухопутных
механик. В первоначальном переносе 0.7.1 неизвестная история урона и offense
явно принимались равными 0. С 0.7.5 offense фиксирован на согласованной
середине шкалы CP — 5; порог раненого участника равен 40 HP. История остаётся
нулевой в 0.7.1–0.7.5. С 0.8.0 реальная история передаётся через AI ABI 6;
эти входы не восстанавливаются через текущую опасность или геометрическую эвристику.
Индекс CP и предварительные оценки были зависимостями переносимых механизмов;
их стоимость измерялась вариантом `common`, а не приписывалась комбинациям.
Пул состояний и упаковка памяти не входили в первоначальный перенос 0.7.1.
Их последующий перенос описан ниже.

Граница поддержки и обязательные шаги при добавлении новых типов перечислены
в [профиле расширения составов](combat-ai-contract.md#поддерживаемый-профиль-и-расширение-составов).
Статус «перенесено» в этой карте относится к нынешним пяти типам и их
поддерживаемым механикам. Он не распространяется автоматически на новый
состав, новые способности или дополнительные домены.
Отдельно зафиксированы [история урона и профиль offense](combat-ai-contract.md#история-полученного-урона-и-профиль-offense):
прошлый урон поступает из реального состояния ядра, offense пока фиксирован
на 5. Нулевой истории по умолчанию для неизвестного прошлого больше нет:
снимки/реплеи прежней версии отклоняются.

### Происхождение механизмов хранения

Закреплённый `CvTacticalAI.h`: `SPathFinderStartPos` (593),
`TCachedMovePlots`/`TCachedRangeAttackPlots` (674–675), байтовые поля
`CvTacticalPlot`, двухкомандный `SComboMove`, `CvTactPosStorage` (1018).
`CvTacticalAI.cpp`: `getReachablePlotsForUnit` (8140),
`updateMovePlotsIfRequired` (8667), `refreshVolatilePlotProperties` (8995),
копирование позиции (9166), `updateMoveAndAttackPlotsForUnit` (9247),
применение назначений (9400–9640), сброс пула при смене игрока (10349, 10763).

Отличия представления обусловлены физической моделью симулятора:

- В ключе достижимости убитые ID однозначно задают освобождённые вражеские
  клетки: враги в течение локального поиска не перемещаются. Дополнительно
  учитываются видимые живые враги, поскольку они меняют конечные клетки
  путей и зоны контроля. Своя занятость в `move_intents` игнорируется.
- В кэше сохраняются намерения до фильтра области; текущие `valid`,
  `blocked` и предел назначения проверяются при использовании, как и прежде.
  Это предотвращает замораживание области до нового контакта. Кэш дальних
  целей также хранит геометрию без привязки к прежнему обзору и живым целям.
- Синхронизация позиции ленивая: собирается актуальное физическое
  представление, затем обновляются изменившиеся тактические поля. Полные
  обходы физического состояния не объявляются устранёнными.
- Пул хранит полноценные физические ветви, которых нет в этой форме у CP.
  Они владеют памятью и картой; `clone_into` заменяет состояние целиком,
  очищает экспортные указатели и кэши. Слот с отвергнутым кандидатом
  переиспользуется, не меняя бюджет принятых позиций.
- Полный сброс пула при смене игрока сохранён. Дополнительный полный сброс
  при смене карты нужен многократно используемому контексту симулятора;
  оригинальный CP работает с одной картой текущей игры.

Это перенос хранения и зависимостей, без новых эвристик тактики.
Возможности Civ V вне поддерживаемого профиля остаются открытой границей,
а последующие решения координатора — отдельной работой CP-07.

### Проверки и свежие замеры хранения

Исходная текущая версия зафиксирована коммитом `b6ace93`. Отдельно
пересобран старый порт из `cp-transfer-20261102/baseline` (ABI 5).
Старые входы используются как нагрузки; их прежние решения не являются
эталонами качества. Недостающая история урона для такого сравнения явно
задана нулём только внутри измерительного инструмента.

Стенд `tools/measure_tactical_storage.py`: девять исторических нагрузок,
12 свежих индивидуальных/исторических сценариев и 24 групповых запроса
с 1/4/8/13 участниками, открытой местностью/проходом/дальним сближением
и обоими режимами тумана. Один прогрев, пять измерений каждой версии;
MSVC x64 `/O2`, последовательные процессы. Компиляция, создание запроса,
загрузка DLL и исполнение результата находятся вне измеряемого вызова.
В вызов входят упаковка ABI, создание адаптера/геометрии и сам поиск.
Первый вызов с выделением пула измеряется отдельно от прогретого вызова.
Пик RSS относится ко всему процессу, включая ранее загруженные версии и
исполнение проверки; он не используется для сравнения памяти версий.

Полный отчёт, исходные измерения, хеши входов и версий:
[storage-transfer-20261102](../artifacts/combat-ai/storage-transfer-20261102/report.md).
Инструментированные DLL отделены от замеров скорости.

Нативные проверки `cp_storage_caches`, `cp_storage_boards`,
`cp_storage_pool` проверяют актуальность кэшей после контакта/движения/убийства,
совпадение обновлённых свойств с полным пересчётом и повторное использование
контекста на разных картах и лимитах. Это проверки представления и
совместимости, не доказательство оптимальности тактического решения.

веб-матчи удалены, их планы не используются как эталон качества.

Нативные группы `cp_area_and_preferences`, `cp_blocker_combinations`,
`cp_forecast_and_danger`, `cp_history_and_admission` проверяют правила отбора: дальний старт с полезным
назначением, дальние назначения только BLOCKED, видимость, равные оценки,
неизменность блокировщика, освобождение клетки несоседним участником,
немоделируемый блокировщик, обмен, завершённое прикрытие, исходную передачу
параметров урона, игнорирование занятости в индексе опасности и раздельные
ключи убитых. Остальные нативные группы проверяют исполнимость планов,
атаки, контакт, бюджеты, детерминизм, туман, чётность и wrap.
`cp_area_capacity` проверяет вставку центра перед соседями, когда для
последнего участника осталось только два места из 255. Чистые прогнозы
силы также сверяются с неизменённым ядром на 75 сочетаниях типов и ранений.

Старые проверки, требовавшие отсутствие тактических запросов для дальних
начальных позиций, заменены проверкой сохранения доступности всех юнитов
для последующего подхода. Эпизод 051 отдельно проверяет, что дальняя цель
не притягивает произвольного ближнего противника вне области CP, а выбор
этого ближнего противника целью допускает атаку всадника. Это проверка
границы области, а не требование сохранить прежнюю тактическую последовательность.

Замеры: `tools/measure_cp_transfer.py`. Варианты:

- `baseline`: сохранённые рабочие исходники до переноса, пересобранные /O2;
- `common`: новые общие оценки и зависимости, без области и сборки комбинаций;
- `area`: common с областью/фильтром назначений CP;
- `combos`: common с комбинациями и объединением завершений CP;
- `combined`: рабочий поиск с обоими механизмами.

Отключённая область в абляции означает доступность всех клеток; отключённые
комбинации исключают и пары освобождения/обмена, и depth-first объединение
завершений. Это контролируемые отключения механизмов, не альтернативные
эвристики для внедрения. Планы исходного поиска не являются эталоном
оптимальности. Различия планов и no_plan исследуются как результаты поиска.

Корпус из 49 сохранённых запросов, пять повторов девяти основных входов,
обычная и инструментированная сборки. Время включает упаковку Python→ABI,
создание адаптера, индексов и весь поиск; компиляция и проверка плана
исключены. Непустые планы на входах со snapshot исполняются ядром с проверкой
урона, движений и конечного состояния. Большой вход имеет только
PlanningState, поэтому для него не заявляется проверка исполнения.

Воспроизведение из архива исходников baseline:

```powershell
python tools/measure_cp_transfer.py prepare --out build/cp-transfer-repeat --baseline artifacts/combat-ai/cp-transfer-20261102/baseline
python tools/measure_cp_transfer.py build --out build/cp-transfer-repeat
python tools/measure_cp_transfer.py run --out build/cp-transfer-repeat --suite differential
python tools/measure_cp_transfer.py run --out build/cp-transfer-repeat --suite timing --repeats 5
python tools/measure_cp_transfer.py run --out build/cp-transfer-repeat --suite metrics
python tools/measure_cp_transfer.py report --out build/cp-transfer-repeat
```
