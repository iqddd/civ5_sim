# Следующий этап: увеличить бюджет работающего PPO

2026-11-05. Направление после ppo-controlled-updates. Не запущено.

## Что хотим получить

Проверить, продолжается ли рост силы при увеличении опыта. Текущий кандидат
update 43 имеет 91/256 argmax-побед над обычным CP (35,55%), BC — 51/256.
Ближайший практический ориентир — приблизиться к 50% побед; обязательный
критерий полезности — положительный парный прирост относительно update 43.
Это ориентир, не обещание. Цель проекта 75% сохраняется, но темп роста
не экстраполировать линейно из одного успешного опыта.

Один запуск **до 4 194 304 новых решений или 14 400 с активного времени**.
Не серия новых микродиагностик и не перебор гиперпараметров. При прежней
скорости ориентир активного времени около 2,8 часа, не гарантия; подготовка
и оценки учитываются отдельно. Изменение частоты побед/длины эпизодов
может изменить скорость.

## Инициализация и данные

  и Adam counter 2076. Policy hash:

- Seed 17, новый явно записанный namespace для training cases и отдельный
  детерминированный RNG shuffle. Это контролируемое продолжение model/Adam,
  не заявление о точном resume прежней последовательности RNG.
- Прежние 57 training-worlds, 228 crops. Новые эпизоды по ID начиная с
  **22912**, после всех собранных в завершённом опыте, а не только после

  Случайные совпадения физических стартов возможны: считать и сообщать их,

- Контакт/разделение и стороны поровну; 10×10, воин+лучник, 100 HP,
  30 раундов, fog/random damage. Только штатный CP-противник с теми же
  planning/callback, SearchConfig и привилегиями. Закрытый test не открывать.

Выбор update 43 следует уже принятому development-правилу. Разница с
последним update 90 всего одна победа из 64 и не доказывает переобучление;
это не основание вводить обязательную остановку каждые полмиллиона решений.

## Обучение

Сохранить проверенные параметры без дополнительного тюнинга:

| Параметр | Значение |
|---|---|
| Policy / critic | C/GRU, shared encoder, обе головы обучаются |
| Reward | победа 1, ничья/поражение 0, без shaping |
| Gamma / lambda | 1 / 1, полные эпизоды, Monte Carlo |
| LR | постоянно 1e−5 |
| Adam | betas 0,9/0,999; eps 1e−5; weight decay 0 |
| Rollout | минимум 8192 реальных решений, законченные волны |
| Среды / workers | 128 / 4 |
| Epochs | до четырёх |
| Minibatch | 1024 реальные позиции; остаток по фактическому размеру |
| Microbatch / fragment | 8 последовательностей / 128 позиций |
| Clip / value coefficient / entropy coefficient | 0,2 / 0,5 / 0 |
| Gradient norm | 0,5 |
| Приём шага | полный KL(old || current) ≤0,015 по свободным состояниям |

При превышении KL — восстановить model/Adam и закончить текущий rollout.
Три подряд rollout без принятого шага — остановка с отдельной причиной.
Free/forced, advantage normalization, GRU prefixes и precision — без изменений.
Не вводить LR decay: сначала проверить масштабирование работающего режима.

Все принятые и отвергнутые попытки входят в активное время. На временной
границе завершить начатую попытку и проверку, принять/откатить, остановиться.
На границе решений завершить волну; уменьшенный последний rollout обучить,
если осталось время, без дополнения старыми данными. Номер rollout продвигается
даже при нуле принятых шагов. Родительские артефакты сохранить неизменными.

## Оценки и остановка

До начала обучения зафиксировать правило: development argmax против CP —
основная метрика; sampling и greedy контрольные. Прежний набор 64 матчей
на соперника, оба режима. Оценивать на нуле и после каждых **524288 новых
решений** (восемь плановых точек), плюс последний checkpoint при ранней
остановке. Начальную оценку update 43 переиспользовать при том же evaluator.

Кандидат — максимум argmax wins против CP, tie — более ранний. Родитель
update 43 входит в кандидаты. Не выбирать по sampling, greedy, training
win rate или дополнительным 256 матчам. Отдельно хранить последний
checkpoint и лучший development checkpoint с соответствующим Adam.

Не вводить раннюю остановку по одной-двум неудачным точкам на 64 матчах.
Это ограниченный заранее опыт с жёстким бюджетом. На 1, 2 и 4 млн новых
решений показать пользователю кривую и фактический ETA, без автоматического
перезапуска, увеличения лимита или смены параметров.

После выбора кандидата один раз использовать прежние 256 дополнительных
validation-матчей, argmax против CP. Главная пара — **update 43 против
нового кандидата**, а не BC против нового кандидата. Родительский результат
91/46/119 переиспользовать при неизменном evaluator; BC показывать только
для общей истории прогресса. Если evaluator изменился, обе стороны пары
должны оцениваться одной версией.

Публиковать парный 95% bootstrap CI по parent-worlds, W/D/L, контактные/
разделённые старты и обе стороны. Ничьи победами не считаются. Положительная
нижняя граница относительно update 43 поддерживает полезность продолжения;
пересечение нуля означает неопределённый результат на этом наборе.
При совпадении кандидата с родителем не выдавать [0;0] за проверку обучения.

Оба validation-набора уже используются для разработки; не называть их
новым test или независимой подтверждающей выборкой. Новые training seeds,
новые миры для окончательного подтверждения и открытие test — отдельный
этап после оценки устойчивости метода. Seed 42 автоматически не запускать.

## Стоимость и проверки

Использовать компактное хранение и ограниченную retention завершённого
опыта; сохранять initial, лучший, последний и оценённые checkpoints,
подробные rollout для начальной/последней проверки и технических ошибок.
Не сохранять тяжёлые дубли encoded/hidden для каждого rollout.

Полный KL сейчас занимает около 60% PPO-времени. Не сокращать частоту
проверки одновременно с увеличением бюджета. Ускорять вычисление можно
при подтверждённой численной эквивалентности; отдельную кампанию
оптимизации перед этим запуском не назначать.

Для изменённой инициализации нужны точечные проверки: model/Adam совпали
с update 43, critic не сброшен, шаги Adam продолжаются с 2076, новый бюджет
начинается с нуля, training не использует holdout/validation, новые streams
не воспроизводят уже пройденный участок. Прежние успешные CP и rollback
тесты без изменения соответствующего кода не повторять. Full suite не нужен.
GPU-фазы измерять по действующей AGENTS.md, не считать wall time обучения
временем непрерывной GPU-работы и не дробить фазы искусственно ради исключения.

Если сила продолжит расти, следующий разумный шаг — проверить устойчивость
другим training seed и масштабировать дальше. Если train растёт, а обе
validation-кривые стоят, разбирать обобщение/покрытие. Если все кривые стоят,
уже есть основание менять обучение или оценку состояний, вместо ещё одного
слепого увеличения бюджета. Размер армий, архитектуру и награду в текущем
опыте не менять: иначе потеряем ответ на вопрос, масштабируется ли найденный режим.
