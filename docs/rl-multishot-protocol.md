# D0-M: многошаговая победа без манёвра — спецификация v1

Дата: 2026-11-04. Зафиксированный протокол D0-M. Статус и результаты запуска
публикуются отдельно в `artifacts/rl/diagnostic-multishot/report.md`.
Машиночитаемые параметры: `configs/rl-diagnostic-multishot.spec.json`.
Этот JSON не является готовым конфигом существующего runner.

## 1. Проверяемый результат и границы

Проверить, может ли policy после одношагового D0 освоить победу, требующую
нескольких выстрелов и смены ходов, используя только терминальную награду.
Успех относится к этой задаче; он не доказывает освоение D1, манёвра, выбора
цели, противодействия атакующему врагу или полезность GRU.

В D1 было 0 побед в 4096 тренировочных эпизодах. На его dev пассивная политика
дала 128 ничьих, attack-or-end-turn — 127 ничьих/1 поражение, greedy — 128 побед.
Поэтому здесь убирается потребность искать манёвр и координировать два юнита.
Новая задача не является чистой абляцией одного фактора относительно D1.

Исходные D0, D0-one-decision и D1 сохраняются, их статусы не пересматриваются.
Никакого автоматического перехода в D1, второго training seed, изменения HP
по результатам policy, подбора LR или продления бюджета.

## 2. Среда

| Параметр | Значение |
|---|---|
| Карта | Плоская 6×6 из исходных D0-расстановок |
| Learner | Один лучник, 100 HP |
| Противник | Один воин, 40 HP на старте сценария |
| Политика врага | Только end_turn; без перемещения и атак |
| Видимость, случайный урон | Включены, обычные правила ядра |
| Начальное положение | Есть легальный ranged по единственной цели |
| Горизонт | 4 раунда, тот же счётчик 2×max_rounds, что в DecisionEnv |
| Терминал | Уничтожение армии либо обычный лимит раундов |
| Награда | Победа +1, поражение −1, ничья 0; промежуточная 0 |
| Специальный лимит learner decisions | Отсутствует |
| Лимит команд за ход | 2000; превышение — техническая ошибка |

Обычные лечение, расход движения, возможность повторной атаки и смена ходов
не меняются. Доступен полный публичный список легальных действий: не удалять
move/skip/fortify/end_turn, не добавлять принудительный end_turn после выстрела.
Нет награды за выстрел, урон, раннюю победу или штрафа за ожидание. При gamma=1
поздняя победа равноценна ранней; скорость победы — только описательная метрика.

Ожидаемая простая последовательность: ranged → end_turn → ranged, иногда ещё
end_turn → ranged. Это не фиксированный сценарий действий для модели.
После её перемещений могут потребоваться другие команды; обучение остаётся
on-policy, без демонстраций и подмешивания команд контрольного агента.

## 4. Модель и инициализация

Модель C без изменения архитектуры: 1 375 362 параметра, 73 tile features,
33 globals, 20 previous-action features, четыре hex-блока ширины 128,
context 309→256→256, GRU 256, action scorer 529→128→1,
value head 256→128→1. Точные параметры берутся из разрешённого D1-конфига.

Источник всех обучаемых параметров policy **и value**:
`artifacts/rl/diagnostic-one-decision/seed-17/checkpoints/update-000006.pt`.
Проверить каждый тензор побитово. D1 update 8 не используется. Не сбрасывать
value head, не замораживать encoder, не делать предварительный value-only fit.
Перенос critic — сознательно сохранённая настройка: в этом опыте проверяется
новая задача, а влияние инициализации critic отдельно не выделяется.

Создать свежий Adam, новые training RNG от seed 17 и нулевые счётчики этапа.
GRU обнуляется только на старте эпизода, сохраняется между его решениями.
Исторические optimizer/RNG не загружать. Сохранить исходный checkpoint hash,
hash тензоров и доказательство пустого Adam.

BF16 только в прежних spatial dense операциях; GRU, головы, outputs и loss
FP32, параметры FP32. Spatial block 32, TF32 выключен; остальные numerics и
проверки behavior/replay — ровно как в D1. Архитектура A/B не запускается.

## 5. PPO и расписания

| Параметр | Значение |
|---|---|
| Среды / CPU workers | 128 / 4, по 32 среды на worker |
| Rollout | ≥8192 новых learner decisions; завершать начатую волну |
| Policy во время сбора | Заморожена; только завершённые эпизоды |
| Return | Полный терминальный Monte Carlo, gamma=lambda=1 |
| Advantage | Нормировка по всем valid tokens rollout, epsilon=1e−8 |
| PPO clip | 0,2 |
| Value loss | MSE без 1/2, coefficient 0,5, без value clipping |
| Entropy | Categorical / log числа легальных действий |
| Эпох | Не более 4 |
| Фрагмент GRU | Не более 128 решений, полный current-weight prefix без градиента |
| Minibatch | 1024 реальных решения на Adam step |
| Microbatch | Не более 8 фрагментов |
| Gradient clipping | Global norm 0,5, один раз перед Adam.step |
| Adam | betas=(0,9; 0,999), eps=1e−5, weight_decay=0 |
| KL | Текущий sampled estimator по всему rollout после каждого шага |
| KL stop | >0,015: завершить оптимизацию rollout, сохранить превышающий шаг |

Суммировать loss с весом по числу valid tokens всего minibatch. Padding не
учитывать. Остаток эпохи нормировать по фактическому числу tokens. При разрезе
фрагмента пересчитать prefix с текущими весами; разные эпизоды не склеивать.
Остатки rollout после KL-stop не переносить в следующий update. Сохранять
число собранных решений отдельно от предъявлений градиенту и Adam steps.

LR: 0,0003→0,0001; entropy coefficient: 0,01→0,002, линейно за 2 000 000
**новых решений D0-M**, далее постоянны. Счётчик начинается с нуля, snapshot
расписаний делается до сбора rollout и сохраняется до конца его оптимизации.
Оценки, эпохи, шаги Adam и прошлые 49 152 решений D0 не двигают этот счётчик.
Resume D0-M восстанавливает Adam/RNG/счётчик без сброса. Нет adaptive LR,
KL rollback, shaping, reward normalization или повторного использования
старого rollout.

## 6. Оценки, критерии и остановка

До обучения оценить на неизменных 128 dev games:

- Исходную случайную сеть seed 17 из первого D0 initial.pt.
- Перенесённую сеть D0 update 6 до нового обучения.
- Алгоритмический ranged/end_turn контроль и пассивный end_turn контроль.

Policy mode sample, temperature=1, фиксированные dev sampling seeds;
для каждого checkpoint ровно те же cases/seeds. Контрольные агенты не
используются как демонстрации. Сохранить outcomes всех оценок.

Если transfer уже выигрывает ≥122/128, завершить с отдельным статусом
`solved_at_transfer`, без обучения. Это означает достижение целевого поведения
до нового опыта, а не успех нового обучения. Порог на исходной сети не служит
основанием усложнять задачу автоматически.

Иначе выполнить первый training rollout. Если в нём нет ни одной победы,
сохранить его, метрики и примеры; завершить **до Adam.step** со статусом
`no_positive_reward_in_initial_rollout`. Это диагностическая остановка по
данному объёму выборки, не доказательство невозможности обучения. Счётчики
потраченных решений/времени включают этот rollout. Победы не искать
автоматическими дополнительными rollout и не подмешивать reference episodes.

После каждого выполненного update — полная оценка 128 dev games. Успех обучения:
≥95% побед, то есть **минимум 122/128**, на **двух последовательных post-update
оценках**. Неуспех сбрасывает streak; baseline в него не входит. Неполная
оценка — техническая незавершённость, не отрицательный результат.

Гейтов первого выстрела, скорости победы и прироста на 20 п.п. нет. Первый
выстрел по конструкции не победный; требовать 20 п.п. невозможно при сильном
transfer baseline. Прирост над random и transfer всё равно публикуется,
с парным percentile bootstrap 95%, 10000 samples, seed 20261103, cluster по
64 layout_id с сохранением обеих сторон и пары policies. Интервал описательный,
не дополнительный gate. Повторные оценки на одном dev не являются независимыми
подтверждениями и не дают одновременную 95% гарантию.

Лимиты одного seed: **8 updates**, **1800 секунд обучения**. До нового update
проверять оба; уже начатый update завершить и оценить. Время включает collection,
PPO, KL, сохранение и обслуживание update; evaluation, подготовку корпуса,
прогрев до первого rollout и паузы учитывать отдельно. Число решений ограничено
косвенно восемью завершёнными rollout; overflow явно публиковать, не обещать
точно 65536 решений. Приоритет: завершить pending evaluation → success →
update/time limit → новая итерация. После последнего допустимого update одна
успешная оценка не достаточна; дополнительный update не разрешён.

## 7. Диагностика и артефакты

Каталог нового опыта: `artifacts/rl/diagnostic-multishot/seed-17/`.
Сохранить source archive/passport, resolved config, manifests, checkpoint
initial и каждый update, optimizer/RNG, pending evaluation, метрики JSONL,
CPU/RAM/NVML telemetry. Resume должен завершать pending evaluation до
следующего update и восстанавливать метрики идемпотентно.

Помимо W/D/L и return, записывать:

- Число выстрелов, ходов и learner decisions до исхода; долю побед с ≥2
  выстрелами; на контрольных траекториях победа за один выстрел — ошибка среды.
- Вероятность/выбор ranged при доступности, действия после первого выстрела,
  переход к следующему своему ходу и повторный выстрел. Для каждой условной
  метрики хранить числитель/знаменатель; отсутствие случая — null, не 0.
- Разделить повторный выстрел вообще и повторный выстрел при сохранённом огневом контакте: перемещения policy меняют посещённые состояния.
- Actions by kind, урон, восстановление HP врага, остаточные HP, причины ничьих.
- Mean/std/min/max return, old_value и raw advantage; explained variance
  (null при нулевой дисперсии return); нормированный advantage и loss components.
- Размер каждого Adam step, LR/entropy, KL после шага, norm до clipping,
  изменение весов L2, эпохи начатые/завершённые, tokens и затраты времени.
- Проверку численного behavior/replay до оптимизации с полной категорической
  вероятностью, как в D1; при несоответствии — техническая остановка.

Сохранить детерминированно выбранный минимальный episode_id для каждого
наблюдавшегося исхода, отдельно кратчайшую и самую долгую победу (ties по id).
Нет исхода — явно отметить отсутствие, не подменять другим. Воспроизвести
все сохранённые реплеи с проверкой результатов и каждого state hash.

## 8. Проверки реализации и переход дальше

До исследовательского запуска нужны тесты нового корпуса, отсутствия
one-decision termination, сохранения GRU между решениями и сброса между
эпизодами, терминальных labels без shaping, веток `solved_at_transfer` и
`no_positive_reward_in_initial_rollout`, границ 121/122, streak/reset,
лимитов. Resume-тесты исключены по указанию пользователя; механизм resume сохраняется. Повторно использовать прошедшие D1
проверки token packing, prefix, CPU/reference equivalence и CUDA/BF16 replay;
после изменения runner — выполнить целевые regression tests без resume-тестов.

Не отключать strict config/provenance checks ради нового mode: добавить
явный поддерживаемый протокол. Технические ошибки не считать ничьими или
неуспехом RL. Конфиг и спецификация замораживаются до baseline policy evaluation.

Итоговые статусы: `solved_at_transfer`, `passed`, `failed_update_limit`,
`failed_training_time_limit`, `no_positive_reward_in_initial_rollout`,
`invalid_dataset`, `technical_error`; graceful pause не является итогом.

При успехе следующим отдельным протоколом можно добавить необходимость
одного перемещения до атаки. При неуспехе анализировать первый исчезающий
элемент последовательности и value-калибровку; не объявлять пользу/бесполезность
памяти. Абляция перенесённого critic, seed 42, возврат в D1 и конечные test
остаются за пределами этого этапа. Выбор checkpoint для возможного следующего
этапа — последний, завершивший streak, либо исходный transfer при соответствующем
статусе; не лучший по просмотру отдельных dev-результатов.

## Уточнение метрики сохранённого огневого контакта

После первого выстрела фиксируются публичные ID и позиции лучника и цели.
На первом решении learner в следующем своём ходу возможность возникает,
если оба юнита живы, позиции после выстрела не менялись, цель присутствовала
во всех промежуточных наблюдениях learner и соответствующий ranged легален.
Расход атаки в предыдущем ходу игнорируется. Измеряются достижение возможности
относительно первых выстрелов, немедленное использование относительно возможностей
и средняя вероятность этого ranged. Для каждой метрики сохраняются числитель
и знаменатель; при нуле возможностей условные показатели равны null. Причины
отсутствия возможности (перемещение, потеря видимости, уничтожение, завершение
эпизода, отсутствие легальной атаки) не являются отказом стрелять. Видимость
между наблюдениями не утверждается. Кратчайшая/самая долгая победа выбираются
по learner decisions, ties по episode_id.
