# Архитектура RL

Справочник реализации, сверенный с исходниками 11 ноября 2026 года. Условия
конкретного опыта задаёт его конфигурация и протокол из
[журнала экспериментов](experiment-ledger.md). Базовый `rl-v1` и поздние
опыты BC/PPO имеют разные награды, бюджеты и настройки исполнения.
[Первоначальная спецификация](rl-v1-spec.md) сохранена как исторический вход
конфигураций; её curriculum и старые пути модулей не задают текущее устройство.

## Модули и зависимости

| Пакет | Ответственность |
|---|---|
| `civ5rl.core` | Контракты входов, schema/encoding, модель, агент, `DecisionEnv` |
| `civ5rl.engine` | Collector, shared slots, PPO/BC, последовательности, управление запуском, ресурсы |
| `civ5rl.protocols` | Корпуса и случаи, диагностики, оценки, ограничения протоколов |
| `civ5rl.experiments` | Сценарии опытов, общая подготовка и выполнение оценочных матчей |
| `civ5rl.provenance` | Паспорта, checkpoint/lineage, миграции, валидация конфигураций |
| `civ5rl.reporting` | Анализ сохранённых исходов, отчёты и парный bootstrap |
| `civ5rl.deploy` | Упаковка и управление удалённым исполнением |

`core` не зависит от `engine` или `protocols`; `engine` не импортирует CLI
из `tools/` и сценарии экспериментов. Collector workers загружаются без Torch.
Новый код использует канонические пути, например `civ5rl.core.observation`,
`civ5rl.core.model`, `civ5rl.engine.collector`, `civ5rl.engine.ppo` и
`civ5rl.provenance.checkpoint`. Существующие алиасы плоских импортов — свойство
совместимости реализации, а не рекомендуемая структура новых модулей.

## Информация и память

Policy получает публичную карту, свои юниты, видимых врагов, маску обзора,
начальные составы, публичное время, собственные команды и историю наблюдений.
Скрытые позиции, смерти/HP, приватные флаги врага, RNG, seeds размещения,
`spawn_candidates`, метаданные сценария и CP danger не входят в её признаки.
Critic использует ту же историю. Учебные метки и исход боя не являются входами.
При одинаковой публичной истории признаки, recurrent state и упорядоченный
список команд должны совпадать независимо от скрытого физического состояния.

Явная память хранит ID ранее виденного врага для сопоставления наблюдений,
тип, последнюю клетку, наблюдавшиеся HP и время. Сырой ID не подаётся как
числовой признак. Невидимая запись остаётся устаревшим контактом: скрытая
смерть и повторная видимость пустой клетки не стирают историческое наблюдение.
Это отличается от выбора тактических целей координатором CP.
Возраст измеряется ходами противника: `enemy_clock=floor((turn+side)/2)`;
в признаках он ограничен 32. Память энкодера и GRU обнуляется при новом бое.
GRU обновляется на собственных решениях, включая вынужденные действия;
на ходе противника отдельного вызова сети нет.

## Тензоры

Имена и ширины объявлены в `civ5rl/core/schema.py`, границы encoded-входов —
в `civ5rl/core/encoded_layout.py`. Ниже указаны формы после пакетирования;
`N=width*height<=256`, `A` — число легальных команд в конкретном состоянии.
Карта не отражается и не вращается; соседство учитывает `row_parity`.

| Вход | Форма | Содержание |
|---|---|---|
| cells | `[B,N,73]` | Ландшафт, обзор, свои/видимые юниты, устаревшие контакты |
| globals | `[B,33]` | Пять счётчиков составов по типам и восемь скаляров |
| previous | `[B,20]` | Предыдущая собственная команда либо START |
| neighbors | `[B,N,6]` | Индексы шести соседей с обозначением отсутствующих |
| sources / targets | `[B,A]` | Клетки источника и цели команды |
| action_features | `[B,A,17]` | Вид команды, тип юнита, относительная геометрия и наличие клеток |
| masks | по клеткам/командам | Исключение дополнения из pooling и распределения |

Состав 73 каналов, в порядке конкатенации:

| Поля | Каналов | Кодирование |
|---|---:|---|
| terrain / elevation / feature | 7 / 4 / 9 | One-hot, включая отсутствие feature |
| Реки / существование соседей | 6 / 6 | Биты по направлениям |
| x, y / проходимость | 2 / 1 | Координаты в `[-1,1]`, бит проходимости |
| Обзор / возраст обзора / когда-либо видели | 1 / 1 / 1 | Бит, `min(age,32)/32`, бит |
| Тип своего / состояние своего | 5 / 8 | One-hot; HP/100, moves/240, четыре флага, два счётчика урона/100 |
| Тип видимого врага / состояние | 5 / 2 | One-hot; HP/100, fortified |
| Устаревшие контакты: число / свежий возраст / средние HP | 5 / 5 / 5 | По типам: count/8, `min(age,32)/32`, mean(HP)/100 |

Общие признаки: начальные свои/вражеские составы, живые свои, видимые враги,
когда-либо виденные враги — пять векторов по пять типов, каждый делится на 8.
Затем в варианте C идут `turn/(2*max_rounds)`, время после прошлого наблюдения /32 с
ограничением, начало своего хода, width/16, height/16, side==0,
random_damage, max_rounds/60; в варианте C2 первый и последний скаляры времени
заменены на ограниченные `min(turn/120, 1)` и `clip((2*max_rounds-turn)/120, 0, 1)`.
Вместимость армии 13 в target-scale не меняет делитель 8 и schema признаков.

Предыдущая команда: 8 one-hot (семь видов и START), 6 one-hot (пять типов и
NONE), четыре координаты источника/цели и два бита их наличия. Источник
запоминается до исполнения, цель — приказанная, даже при прерванном движении.
Список действий сортируется; padding не создаёт команды. Усечение списка,
top-k по CP или отбор по истинной скрытой опасности не допускаются.

## HexEncoder, GRU и головы

Базовая модель C имеет 1 375 362 параметра, расширенная C2 — 2 166 722 параметра
(8 hex-блоков вместо 4 и в каждом блоке 4-головое внимание `CellUnitAttention`
от всех клеток к клеткам с публично известными юнитами — своими живыми, видимыми
врагами и устаревшими контактами — с обучаемым смещением по 16 корзинам
гекс-расстояния через детерминированный `BucketBias`). Варианты A/B/C/C2
определены в `core/variants.py`; выбор варианта фиксируется конфигурацией и checkpoint.

`Linear(73,128)` и GELU проецируют клетки. Четыре (в C) или восемь (в C2, с дополнительным остаточным блоком `CellUnitAttention` после обмена соседями) направленных hex-блоков
ширины 128 выполняют обмен с шестью соседями и residual MLP `128→256→128`:

```text
m_i = GELU(LayerNorm(W0*x_i + sum_d(W[d+1]*x_neighbor(i,d)) + b))
u_i = x_i + m_i
x_next_i = u_i + Linear(256,128)(GELU(Linear(128,256)(LayerNorm(u_i))))
```

Отсутствующий сосед даёт ноль. Masked mean/max дают 256 признаков;
вместе с globals и previous это 309. Контекстный MLP `309→256→256`
подаёт вход в однослойную GRU ширины 256. Состояние `h` одно на армию,
начинается с нуля и сохраняется между собственными ходами.

Scorer `529→128→1` использует `h` (256), embeddings источника/цели (128+128)
и 17 признаков команды. Critic `256→128→1` выдаёт скаляр без tanh.
Нет dropout или BatchNorm. Policy — один softmax по текущим легальным
командам; дополненные logits равны `-inf`.

Для sampling применяется `log_softmax(logits/T)` в FP32. Температура должна
совпадать в collector, old logp, behavior distributions, PPO ratio, entropy,
KL и behavior replay. Value и внутренние logits сети не масштабируются.
Argmax при положительной T сохраняет выбор; режим и T различаются в кеше
оценок. BF16 spatial / FP32 GRU, heads и loss — используемый поздними опытами
режим исполнения, который задаётся конфигурацией, а не новый dtype schema.

## Среда, collection и PPO

`DecisionEnv` проводит игру от решения learner до его следующего решения
или конца матча, исполняя intervening ход фиксированного соперника.
Лимит раундов — терминальная ничья без bootstrap. Технические ошибки и
незаконные действия не превращаются в проигрыш или ничью.
Reward выбирает протокол: базовый v1 использует win/draw/loss `1/0/-1`,
поздние контролируемые и target-опыты — `1/0/0`.

На сбор фиксируются веса policy. В rollout входят полные эпизоды; начатые
бои завершаются, фактический объём может превысить цель. Поддерживаются
`barrier`, `ready` и явно включаемый `streaming`. Streaming закрепляет бои за
CPU workers, переключается между ними после команд CP, пополняет свободные
слоты и прекращает пополнение при достижении цели/deadline. Один CP-вызов
не делится на части. Разные scheduler/ёмкости могут менять границы rollout:
это не обещание идентичного дальнейшего обучения.

При `gamma=lambda=1` (`complete_episode_monte_carlo`) return каждой позиции
равен терминальному исходу её эпизода $R \in \{0, 1\}$, а сырое преимущество
равно $A_t = R - V_{\text{old}}(s_t)$. При `gamma < 1` или `gae_lambda < 1`
(`discounted_monte_carlo_with_gae`, функции `episode_returns` и
`raw_gae_advantages` в `engine/ppo.py`) целью регрессии критика — как при
коротком прогреве `prepare_critic` на первом сборе, так и в основных PPO-шагах —
служит точный дисконтированный терминальный возврат $G_t = \gamma^{T-1-t} R$,
а преимущество актора вычисляется обратным проходом $\text{GAE}(\gamma, \lambda)$
по завершённому эпизоду ($\delta_t = r_t + \gamma V_{\text{old}}(s_{t+1}) - V_{\text{old}}(s_t)$
при $V_{\text{old}}(s_T)=0$, $r_{T-1}=R$, $r_{t<T-1}=0$ и
$\hat{A}_t = \delta_t + \gamma \lambda \hat{A}_{t+1}$). В обоих режимах
advantage z-нормализуется по всем реальным решениям rollout, включая forced.
Actor, entropy и value усредняются по всем valid tokens. У forced одна
легальная команда: собственные policy-gradient и entropy равны нулю, но
включение этих позиций меняет масштаб среднего. Полный KL контролируемого
режима считается по свободным решениям (`action_mask.sum(-1) >= 2`). В BC
forced сохраняются в истории и исключаются из CE; это отдельное правило.

```text
ratio = exp(logp_current - logp_old)
policy_loss = -mean(min(ratio*A, clip(ratio,1-eps,1+eps)*A))
value_loss = mean((V-G)^2)
H_norm = H(policy)/log(number_of_actions)  # 0 при одном действии
loss = policy_loss + value_coef*value_loss - entropy_coef*mean(H_norm)
```

`SequenceBuffer` (`engine/sequence.py`) хранит offsets эпизодов, числа команд,
chunks и общую сборку входов. Его используют `DemonstrationCache`,
`ResidentDemonstrations` и `RolloutCache`; классы добавляют BC/PPO labels.
Размещение на GPU опционально и проверяет доступную память с резервом.
`gather` ограничивает ширину дополнения команд текущим batch.

PPO выполняется единым циклом `engine/ppo.py` через `BatchedBackend` из
`engine/ppo_fast.py`. Без batched-режима используются нерезидентные входы
и одна последовательность на microbatch; это не отдельный ReferenceBackend.
Перед chunk полный префикс данного эпизода пересчитывается текущими весами
без градиента от `h=0`, затем detach и BPTT на chunk (обычно до 128 шагов).
Префиксы разных эпизодов не смешиваются; кеш пригоден лишь до изменения весов.

Behavior replay проверяется до обновления. Остановка по approximate KL
базового v1 и полный `KL(old||current)` с rollback model/Adam/RNG поздних
протоколов (`step_acceptance="full_categorical_kl_rollback"`) — разные правила;
одно не заменяет другое. Для контролируемого отката поддерживаются два режима
`kl_measurement`:
- `whole_rollout_after_optimizer_step` — полный `KL(old||current)` по свободным
  решениям всего rollout проверяется после каждого `optimizer.step()`.
- `whole_rollout_after_epoch_or_minibatch_spike` — на каждом minibatch внутри
  `BatchedBackend.backward` без дополнительных проходов модели в FP64 считается
  minibatch-прокси Шульмана `k3` (`(r - 1) - log r`, $r = \pi_\theta^{(T)} / \pi_{\text{old}}^{(T)}$)
  по свободным решениям; полный прогон `measure_step_replay()` вызывается в конце
  каждой эпохи PPO либо немедленно при входе в жёлтую зону (`minibatch_approx_kl > minibatch_kl_spike_threshold`,
  по умолчанию `0.010`), подтверждая пачку накопленных шагов в `AdamSnapshot` при
  `full_kl_free <= stop_kl` (`0.015`) или откатывая все неподтверждённые шаги
  от последней проверенной границы через `AdamSnapshot.restore()`.

Размер Adam batch, microbatch, число эпох, критерий принятия, целевой набор
оценки (`development` на 128 случаев или `development_512` на 512 случаев) и
предстартовая проверка временного бюджета (`compute_time_budget_check`) берутся из опыта.

## Значения по умолчанию и настройки опытов

| Настройка | Базовая реализация / rl-v1 | Пример явного выбора |
|---|---|---|
| scheduler | `barrier` | `ready` или `streaming` в runtime/конфиге опыта |
| policy temperature | `1` | `0.5` в `configs/rl-ppo-target-bc-t05.json` и `configs/rl-ppo-c2-h60-gae.json` |
| max_rounds | `30` | `60` в `configs/rl-ppo-c2-h60-gae.json` |
| gamma / gae_lambda | `1` / `1` | `0.997` / `0.95` в `configs/rl-ppo-c2-h60-gae.json` |
| kl_measurement | `whole_rollout_after_optimizer_step` | `whole_rollout_after_epoch_or_minibatch_spike` в `configs/rl-ppo-c2-h60-gae.json` |
| evaluation_purpose | `development` (128) | `development_512` (512) в `configs/rl-ppo-c2-h60-gae.json` |
| spatial_cell_padding | `0` | `256` в target-scale PPO/BC |
| Среды / workers в rl-v1 | 32 / 4 | Результат подбора на конкретной машине |
| PPO batched/resident/compile в rl-v1 | Включены в performance | Режимы backend остаются настраиваемыми |

Padding 256 фиксирует spatial-геометрию смешанных карт 10/12/16;
маски исключают добавленные клетки из pooling/действий. Это не увеличение
физической карты. Нельзя переносить T, padding или runtime-настройки
в старый опыт как незаметную «актуализацию».

## Паспорта, исходники и resume

`provenance/checkpoint.py` сохраняет passport, `sources.zip`, resolved config
и corpus manifest. Источники по умолчанию включают `docs/**/rl*.md`;
`passport_artifacts` дополняет список workspace-relative путями/glob.
Правила ролей сосредоточены в `provenance/identity.py`.

| Проверка | Что сравнивается |
|---|---|
| `verify_frozen_passport` / анализ | Все записанные члены и SHA-256 замороженного архива, corpus, доступный hash resolved config |
| Execution / resume / новые матчи | Замороженные свидетельства, затем текущие исполняемые исходники, config/corpus и среда |
| Миграция | Отдельная именованная политика и allowlist; нельзя считать её обычным resume |

Из execution-role исключены Markdown, reporting/deploy, tests, read-only
report/audit/inspect/benchmark/profiler tools и чистые отчётные модули.
Core, engine, protocols, simulator/map/native, provenance и смешанные runners
остаются закреплены. `experiments/evaluation.py` исполняет матчи и закреплён;
чистый анализ сохранённых результатов вынесен в `reporting/evaluation_audit.py`.
Training/data/match/build entrypoints также входят в execution identity.
Из tools helpers отдельно закреплены `_build_common.py` и
`_imitation_benchmark.py`: первый меняет сборку, второй создаёт демонстрации,
используемые при обучении. Чистые измерительные helpers остаются вне identity.
`passport_artifacts` не возвращает read-only файл в исполняемую роль.

Редактирование или перенос текущего Markdown сами по себе не блокируют
обычный execution comparison. Старые архивные байты всё равно проверяются:
`passport.json` и `sources.zip` не переписываются. Миграционная проверка
`provenance/migration.py` может учитывать Markdown отдельно; утверждение
«любая проверка игнорирует документацию» неверно.

Frozen audit не сравнивает текущее дерево/установленные пакеты/GPU и не
доказывает целостность всех checkpoints или результатов сам по себе.
Нужны также ledger/checkpoint/evaluation checks из
[операторского справочника](rl-operations.md). Исторические паспорта без hash
resolved config остаются такими: отчёт указывает `config_hash_verified: false`.
Перенос кода между модулями меняет execution identity даже при совместимых
тензорах. Совместимость модели не разрешает обход lineage/migration checks.
